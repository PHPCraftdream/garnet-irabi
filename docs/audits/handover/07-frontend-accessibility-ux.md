# Аудит UX / Accessibility фронтенда — IRabi (Slotbook)

Дата аудита: 2026-07-18
Область: `Apps/IRabi/Front` (Islands, Common, Styles) + общие компоненты `garnet-framework/Bundle/Front/Common/Components`.
Метод: построчное чтение React/TSX-кода островов, форм, модалок и общих утилит (DateUtils, Validators, sendPost/asyncJsonThen, useConfirm, Portal), сверка со стилями темы (theme.css) и с PHP-роутами контроллеров (Foreground/Controllers) для проверки ссылок. Изменения в код не вносились.

---

## Резюме

Фронтенд в целом сделан аккуратно: единый источник форматирования дат/времени с учётом часового пояса пользователя (`DateUtils.ts`), метаданные-driven клиентская валидация форм (`FormBuilder` + `Validators`), корректная обработка `503`/maintenance, глобальный `ErrorBoundary` на каждом острове, разумные состояния "пусто" почти везде, мобильная адаптация для IM/Support (master-detail на узких экранах).

Однако есть системная проблема — **у модальных окон нет ни одной реализации фокус-ловушки (focus trap)**: `Portal` — это просто `createPortal` без всякого управления фокусом, а обработка `Escape` продублирована вручную в 5+ разных компонентах (и в паре мест отсутствует вовсе). Также найдено использование деструктивных операций (выдача прав администратора/владельца, блокировка пользователя) без единого паттерна подтверждения, который явно применяется в соседних разделах той же админ-панели. Есть контраст ниже WCAG AA у части текстовых стилей в светлой теме, отсутствие клавиатурного доступа к кликабельным строкам списков (IM, Support), и полное отсутствие мобильной адаптивности у календаря эксперта.

Ниже — находки по приоритету.

---

## Critical

### C1. Модальные окна не имеют фокус-ловушки (focus trap) — фокус "убегает" за пределы модалки
**Где:** `garnet-framework/Bundle/Front/Common/Components/Portal.tsx` (используется всеми модалками приложения — `BookingModal.tsx`, `SlotDetailModal.tsx`, `BalanceAdjustModal.tsx`, `UserDetailPanel.tsx` и др.), `ConfirmModal.tsx`.

`Portal` — это ровно:
```tsx
export const Portal: FC<{children: ReactNode}> = ({children}) =>
    createPortal(children, document.body);
```
Никакого перехвата `Tab`/`Shift+Tab` нет нигде в кодовой базе (grep по всему `Front` и `Components` не находит ни одной реализации focus-trap). Что увидит пользователь: открыв модалку бронирования слота или окно отмены брони и нажимая `Tab`, фокус свободно уходит на элементы страницы **позади** затемнённого фона (например, в меню навигации или в другую кнопку списка), при том что визуально модалка остаётся открытой поверх контента. Для пользователей с клавиатурной навигацией и скринридер-пользователей это означает полную потерю ориентации — можно случайно провзаимодействовать с элементом, скрытым за модалкой.

Дополнительно: при открытии модалки фокус не переводится на первый интерактивный элемент/сам диалог (`autoFocus`/`ref.current.focus()` нигде не вызывается при монтировании диалоговых `div`), а при закрытии фокус не возвращается на элемент, который открыл модалку — стандартное требование WAI-ARIA Dialog Pattern.

### C2. `ConfirmModal` (общий компонент подтверждения, используемый по всему приложению) не закрывается по Escape
**Где:** `garnet-framework/Bundle/Front/Common/Components/ConfirmModal.tsx`.

Это тот самый универсальный "да/нет" диалог, вызываемый через `useConfirm()` — используется, например, в `ExpertBookings.tsx` для отмены брони. У него нет `useEffect` с обработчиком `keydown`/`Escape`, в отличие от `SlotDetailModal.tsx`, `SubGridModal.tsx`, `DetailViewModal.tsx`, `AdminTokensSection`-подобных диалогов (которые слушают Escape вручную, каждый по-своему). Пользователь, привыкший закрывать диалоги клавишей Escape (стандартное поведение для 95% веб-приложений), в этом конкретном диалоге получит "зависание" — Escape не сработает, придётся кликать мышью по кнопке или по фону.

### C3. Модалка "Написать пользователю" в админ-панели полностью лишена диалоговой семантики и Escape
**Где:** `Front/Islands/AdminPanel/UserDetailPanel.tsx`, строки 230–276 (компонент, рендерящий `<Portal><div className="fg-modal-overlay" onClick={onClose}>...`).

В отличие от `BalanceAdjustModal.tsx` (та же папка), у которой ЕСТЬ `role="dialog" aria-modal="true"`, у этой модалки (отправка сообщения пользователю от имени модератора/админа) нет ни `role="dialog"`, ни `aria-modal="true"`, ни обработчика `Escape`. Скринридер объявит содержимое модалки как обычный кусок страницы, не даст понять пользователю, что открылся диалог, и не заблокирует "виртуальный курсор" внутри него. Закрыть можно только кликом по кнопке `×` или по подложке — с клавиатуры Escape не работает.

## High

### H1. Единый паттерн подтверждения нарушен для самых опасных действий в разделе "Пользователи" админ-панели
**Где:** `Front/Islands/AdminPanel/UsersSection.tsx`, строки 176–215 (кнопки `IS_DISABLED`, `IS_MODERATOR`, `IS_OWNER`, `IS_ADMIN`, а также переключатель типа аккаунта user↔expert, строка 159).

В том же самом разделе админ-панели (`AdminTokensSection.tsx`) удаление/отключение токена **обязательно** проходит через `useConfirm()` с вариантом `danger`:
```tsx
const ok = await confirm(t.Admin_Tokens_DeleteConfirm(), {variant: 'danger', confirmLabel: t.Action_Delete()});
```
А в `UsersSection.tsx` кнопки `FlagBtn` для выдачи прав **Owner/Admin/Moderator**, блокировки пользователя (`IS_DISABLED`) и смены роли user↔expert вызывают `setFlag`/`setUserType` **напрямую по одному клику**, без единого диалога подтверждения:
```tsx
onClick={() => setFlag(r.id, 'IS_ADMIN', flag(r.IS_ADMIN) ? 0 : 1)}
```
Что увидит пользователь (администратор): случайный клик по кнопке "Grant" рядом с "IS_ADMIN" в таблице — и пользователю немедленно выданы права администратора без единого предупреждающего экрана. Отменить это можно только повторным кликом (если админ вообще заметит ошибку). Для системы, где выдача роли Owner/Admin — необратимо серьёзное по последствиям действие, отсутствие confirm-диалога при наличии точно такого же паттерна в соседнем разделе того же экрана — явная несогласованность и риск для продакшена.

### H2. Кликабельные строки списков (IM, Support) недоступны с клавиатуры
**Где:**
- `Front/Islands/Im/Components/ConversationList.tsx`, строки 36–75 (`<div onClick={() => onSelectConversation(conv.id)}>`)
- `Front/Islands/Support/SupportWidgetIsland.tsx`, строки ~271 (`<div className="support-widget-ticket-row" onClick={() => openTicket(ticket.id)}>`)
- `Front/Islands/Support/SupportPageIsland.tsx`, строки ~204 (`<div className="support-ticket-row ..." onClick={() => selectTicket(ticket.id)}>`)

Все три списка (диалоги в IM, тикеты в виджете поддержки, тикеты на странице поддержки) реализованы как `<div onClick=...>` без `role="button"`, `tabIndex={0}` и `onKeyDown` (Enter/Space). Пользователь, который работает клавиатурой (Tab для перемещения по странице), физически не может попасть фокусом на строку диалога/тикета и открыть его — вся навигация по спискам сообщений и обращений в поддержку недоступна без мыши. Это блокирует основной пользовательский сценарий (открыть переписку) для клавиатурных пользователей.

### H3. У экспертного календаря (управление слотами) нет ни одной мобильной адаптации — контент будет "сплющен" на телефоне
**Где:** `Front/Islands/ExpertSlots/components/ExpertCalendar.tsx`, строка 272 и весь файл.

Пользовательский календарь слотов (`Front/Islands/SlotsCalendar/WeekGrid.tsx`) корректно переключается на одну колонку на маленьких экранах:
```tsx
className="grid grid-cols-7 gap-0 ... max-md:grid-cols-1 max-md:gap-2 max-md:border-0"
```
А экспертский календарь управления собственными слотами (тот же смысл — неделя из 7 колонок) — нет:
```tsx
<div className="grid grid-cols-7 gap-0 border border-default rounded-lg overflow-hidden" ...>
```
В файле нет ни одного класса `max-md:`/`sm:`/`md:`, нет `overflow-x-auto` для горизонтальной прокрутки. Дочерние колонки дня используют `min-w-0`, то есть будут физически сжиматься, а не скроллиться. На экране телефона (375px) при 7 колонках в общей рамке с бордерами на колонку остаётся ~45–50px — время начала/окончания слота, цена, статус-бейдж и кнопки редактирования/удаления слота (`Pencil`/`Trash2`) будут накладываться друг на друга или обрезаться. Поскольку это основной рабочий экран эксперта для управления расписанием (drag-and-drop слотов, подтверждение/отклонение бронирований), поломка на мобильном — это прямой блокер для экспертов, которые управляют расписанием с телефона.

### H4. Часть текстовых цветов светлой темы не проходит WCAG AA по контрасту — включая критичные сообщения об ошибках
**Где:** `garnet-framework/Bundle/Front/Styles/modules/theme.css` (переменные `--color-text-muted`, `--color-danger`, `--color-status-orange`), используется в т.ч. в `Front/Islands/SlotsCalendar/BookingModal.tsx` (класс `text-danger text-sm` для "недостаточно средств на балансе", строка 182–189) и `BalanceAdjustModal.tsx`.

Измеренные коэффициенты контраста (формула WCAG, требование для обычного текста — 4.5:1):

| Пара | Контраст | Норма WCAG AA |
|---|---|---|
| `text-muted` (#A8A29E) на белом фоне | **2.52:1** | не проходит (нужно 4.5:1) |
| `text-muted` на `bg-surface-alt` (#F4F2EE) | **2.26:1** | не проходит |
| `text-danger` (#cf6a63) на белом фоне | **3.56:1** | не проходит |
| `text-warning` (#c79248) на белом фоне | **2.75:1** | не проходит |
| `status-notice` / оранжевый статус (#b06a4a) на белом | **4.19:1** | не проходит (близко) |
| `text-secondary` (#57534E) на белом | 7.63:1 | проходит |
| Тёмная тема, `text-muted` на surface/page | 6.9–7.7:1 | проходит |

Тёмная тема в порядке, но светлая (тема по умолчанию для новых пользователей) — нет. `text-danger` при 14px (`text-sm`) применяется именно там, где пользователь должен точно понять критичное сообщение — "недостаточно средств для бронирования" (`BookingModal.tsx`, строка 182), ошибки формы бронирования и отмены. Слабовидящие пользователи и пользователи при ярком солнечном свете на экране телефона могут не разобрать текст ошибки.

## Medium

### M1. Денежные суммы нигде не форматируются с разделителем разрядов — кроме одного места, где используется "неправильный" локаль
**Где:** практически весь `Front/Islands/**` — `slot.cost`, `balance`, `amount`, `slot_cost` рендерятся как голое число (`{slot.cost} ₽`) без `toLocaleString`. Единственное исключение — `Front/Islands/AdminPanel/AdminDashboard/AdminPlatformStats.tsx`, строка 31:
```tsx
<div className="admin-dash-stat-value text-success">{revenueThisMonth.toLocaleString()} &#8381;</div>
```
Здесь `toLocaleString()` вызван **без аргумента локали** — то есть результат зависит от локали браузера/среды выполнения, а не от `appLocale()` (утилита `ru-RU`/`en-US`, уже существующая и используемая в `DateUtils.ts`). Для суммы вроде `1234567` пользователь в системе с англ. локалью ОС увидит `1,234,567`, а с русской — `1 234 567`; при этом весь остальной интерфейс (даты) стабильно локализован через `appLocale()`. Более того, все остальные денежные значения в приложении (балансы пользователей, стоимость слотов, суммы возврата, ledger-записи в админке) вообще не группируются по разрядам — баланс "125000 ₽" читается тяжелее, чем "125 000 ₽", особенно в таблицах `LedgerSection.tsx`, `BalancesSection.tsx`, `UserDetailPanel.tsx`, где суммы могут доходить до 5–6 значных чисел. При финальной поставке "под ключ" стоит либо централизовать это через новый хелпер `formatMoney()` в `DateUtils`-подобном модуле, либо явно решить, что для рублей группировка не нужна — сейчас же выглядит как недосмотр (0 из ~25 мест форматируют, 1 из 25 форматирует неправильно).

### M2. `asyncJsonThen` не защищён от не-JSON ответа — сетевые сбои не через сам API дадут неинформативную ошибку
**Где:** `garnet-framework/Bundle/Front/Common/Api/asyncJsonThen.ts`, строка 14: `const data = await d.json() as IApiResponse<T>;`

Обработан только специальный случай HTTP 503 (maintenance, строка 8). Но если запрос долетит до промежуточного прокси/веб-сервера (например, nginx 502/504 при перегрузке или обрыве PHP-FPM, WAF-блокировка, CDN-таймаут) — тело ответа будет HTML или пустой строкой, а `d.json()` бросит `SyntaxError: Unexpected token '<'...`. Этот "сырой" JS-эксепшн всплывёт в `.catch` вызывающего острова, где типовой код — `err?.message || t.General_Error()` (см. `ExpertBookings.tsx`, `ImPageIsland.tsx`) — но `SyntaxError.message` в этом случае будет чем-то вроде `"Unexpected token '<', "<html>..." is not valid JSON"`, и это (нечитаемое, нелокализованное, техническое) сообщение попадёт прямо в toast/алерт пользователю, а не понятный текст об ошибке сети. Общий `ErrorBoundary` здесь не спасёт — падение происходит внутри `.catch`, а не как необработанное React-исключение. Стоит обернуть `d.json()` в try/catch и на неудачном парсинге выбрасывать/показывать общий `Common_RequestError`/`General_Error`.

### M3. Тултип с полной информацией о слоте недоступен с клавиатуры
**Где:** `Front/Islands/SlotsCalendar/SlotCard.tsx`, строки 20–49 — `showTooltip` переключается только по `onMouseEnter`/`onMouseLeave`.

Расширенная информация о слоте (полная длительность, диапазон цены, формат, вместимость — блок с `data-test-id="slot-tooltip-..."`) показывается только при наведении мышью. Клавиатурный пользователь, сфокусировавшийся на кнопке "Забронировать" внутри карточки, этот тултип никогда не увидит (нет `onFocus`/`onBlur`). Смягчающее обстоятельство: та же информация полностью дублируется в `SlotDetailModal.tsx`/`BookingModal.tsx`, которые открываются по клику/Enter на кнопке — то есть данные не теряются полностью, но лишены "быстрого предпросмотра" для non-mouse пользователей.

### M4. Текст `ErrorBoundary` жёстко закодирован на английском и не переведён
**Где:** `garnet-framework/Bundle/Front/Common/Components/ErrorBoundary.tsx`, строки 34–44 — `"Something went wrong"`, кнопка `"Reload"`.

Приложение полностью русскоязычное по умолчанию (бренд "Slotbook", RU-локаль по умолчанию в `DateUtils.appLocale()`), но единственный экран, который увидит пользователь при падении React-дерева острова (краш рендера — не сетевая ошибка, а именно JS-исключение в компоненте), — целиком на английском. Для пользователя, не владеющего английским, это выглядит как "сломанный", нелокализованный кусок интерфейса именно в момент, когда и так что-то пошло не так — худший момент для потери доверия к продукту.

## Low

### L1. `common.less` в IRabi — пустой файл (0 байт)
**Где:** `Front/Styles/common.less`.

Не является багом (все стили реально живут в общих `garnet-framework` less/css-модулях и в tailwind-классах прямо в TSX), но пустой файл в поставке "под ключ" выглядит как незавершённый артефакт/забытая заготовка — заказчик может решить, что кастомизация стилей IRabi здесь и должна происходить, и не найти точку входа. Стоит либо удалить файл, либо оставить явный комментарий, что стили вынесены в framework + inline tailwind.

### L2. "Подтвердить бронирование" (expert) не имеет предупреждения, а "Отклонить" — имеет обязательное поле причины
**Где:** `Front/Islands/ExpertDashboard/ExpertPendingBookings.tsx`, `handleConfirm` (строка 62) vs. `openRejectModal`/`handleReject` (строки 78–101).

Это не дефект — согласованный и логичный паттерн (положительное действие без трения, отрицательное — с объяснением), но стоит зафиксировать явно для заказчика как осознанное решение, а не забытую асимметрию, поскольку в `UsersSection.tsx` (см. H1) аналогичная асимметрия уже является реальной проблемой. Разграничение: здесь "подтвердить" не разрушительно и легко отменяемо повторным действием ("отменить бронирование"), а в `UsersSection.tsx` "выдать права администратора" — действие с несопоставимо более серьёзными последствиями.

## Проверено — без находок

- **Ссылки/маршруты.** Все обнаруженные вызовы `appUrl('/...')` в React-компонентах (`/balance`, `/expert/~slots`, `/bookings`, `/support`, `/slots`, `/im`, `/expert/~confirmBooking` и т.д.) сверены с методами `get__*`/`post__*` в соответствующих контроллерах (`BalanceController`, `ExpertPanelController`, `BookingsController`, `SupportController`, `SlotsController`, `ImController`) — все резолвятся в реально существующие роуты. Twig-шаблонов с прямыми `<a href>` в проекте почти нет (обнаружены только служебные `External.twig`/`NoAccessHeading.*.twig`, без пользовательской навигации) — вся навигация идёт через React-острова.
- **Клиентская валидация форм vs серверная.** `FormBuilder.tsx` строит клиентскую валидацию строго из тех же метаданных поля (`fieldInfo.validation`), которые определяют и серверную валидацию — валидаторы `required`, `email`, `min_len`/`max_len`/`len`, `int`, `min`/`max`, `pattern`, `match` (`Validators.ts`) реализуют идентичную логику, а бэкенд-ошибки (`result.errors`) корректно прокидываются в те же поля через `setFieldErrors`. Расхождений между "что разрешает клиент" и "что отклоняет сервер" не найдено.
- **Форматирование дат/времени и часовые пояса.** `DateUtils.ts` — единая точка форматирования, учитывает часовой пояс пользователя (`__GARNET_USER__.timezone`) с фолбэком на браузерный, использует `Intl.DateTimeFormat` с локалью `ru-RU`/`en-US` в зависимости от `__GARNET_UI_LANG__`. DST и переход недели через воскресенье обработаны явно и с комментариями. Проблем с датами не найдено (кроме денежных сумм — см. M1).
- **Обработка `503`/maintenance.** `asyncJsonThen.ts` отдельно ловит `503` до попытки распарсить JSON и показывает toast через `showToast`/`GlobalToast` — работает корректно (не считая незащищённого `d.json()` в общем случае, см. M2).
- **Состояния "пусто".** Списки бронирований (`ExpertBookings.tsx`, `BookingsTab.tsx`), слотов (`WeekGrid.tsx`/`DayColumn.tsx` — `t.Slots_NoSlots()`), диалогов IM (`t.IM_NoConversations()`/`t.IM_NoMessages()`), ожидающих подтверждения бронирований (`t.Teaching_NoPendingBookings()`) — везде показывают осмысленный локализованный текст, а не пустой блок.
- **Индикация отправки/загрузки.** Паттерн `useSending()`/`SendButton` (блокировка кнопки + спиннер на время запроса, разблокировка в `finally`) применяется последовательно во всех формах — не найдено "зависших" кнопок или дублирующихся сабмитов.
- **Alt-текст / доступность вложений.** `AttachmentDisplay.tsx` — изображения-вложения имеют `alt={att.original_name}` и `aria-label` на кнопке предпросмотра; `SendButton`, `fg-modal-close-x` и большинство иконных кнопок в проверенных файлах имеют `aria-label`/`title`.
- **Drag-and-drop слотов эксперта.** `ExpertCalendar.tsx` — перетаскивание слота для переноса на другой день имеет клавиатурно-доступную альтернативу (кнопка "Редактировать" с `Pencil`-иконкой, открывающая форму редактирования).
- **`prefers-reduced-motion`.** Как минимум одна анимация (`util-badge-pulse`, пульсация бейджа непрочитанных) корректно отключается в `theme.css` через `@media (prefers-reduced-motion: reduce)`.
