## 5. Дублирование зависимостей

1. **`mockery/mockery` (v1.6.12) + `janmarek/mockista` (v1.1.0)** — оба являются PHP-библиотеками для mock-объектов в тестах, зарегистрированы одновременно в `require-dev` `garnet-framework/composer.json`. `mockista` не обновлялся с 2015 года. Рекомендация: определить, какой из двух реально используется в текущих спеках (`Kernel`/`Bundle` kahlan-тестах), и удалить неиспользуемый — это снижает поверхность dev-зависимостей и убирает заброшенный пакет из дерева.
2. **`lucide` (^0.576.0) + `lucide-react` (^0.576.0)** во `FrontBuilder/package.json` — `lucide` (ванильный SVG/JS набор иконок) и `lucide-react` (React-обёртка) добавлены одновременно как прямые зависимости. Если React-компоненты фронтенда используют исключительно `lucide-react`, пакет `lucide` может быть избыточным (либо используется отдельно для non-React частей интерфейса — стоит проверить фактическое использование через grep по импортам `from 'lucide'` вне `lucide-react`).

## 6. Dev-зависимости в проде

Проверено:
- `composer.json` IRabi: `require-dev` содержит `phpstan/phpstan`, `friendsofphp/php-cs-fixer` — стандартный Composer-паттерн `composer install --no-dev` исключает их из vendor/ при продовой установке. Прямых указаний в коде, что эти пакеты подключаются рантаймом (а не только через `scripts`/`bin`), не найдено — рекомендация подтверждена как безопасная при условии, что деплой-пайплайн действительно вызывает `--no-dev` (это стоит перепроверить в самом деплой-скрипте/CI, вне области файлов зависимостей — см. `12-production-readiness-devops.md`).
- `garnet-framework/composer.json`: `require-dev` (`kahlan`, `mockista`, `mockery`, `phpstan`, `php-cs-fixer`) аналогично исключаются при `--no-dev` у потребителя (IRabi), т.к. Composer не устанавливает `require-dev` зависимого пакета транзитивно — это стандартное поведение Composer, риска нет.
- `Tests/package.json` — все зависимости объявлены как `devDependencies`, сам каталог `Tests/` физически отделён от `Bundle/Front`/`FrontBuilder` и не участвует в rspack-сборке фронтенда — подтверждено содержимым `FrontBuilder/package.json`, который не ссылается на `Tests/`.
- Корневой `package.json` IRabi — только `devDependencies`, используется исключительно для IDE, не задействован в `garnet build`.

**Вывод**: явных утечек dev-зависимостей в прод не обнаружено, при условии что стандартные Composer/npm-флаги (`--no-dev`, раздельные `package.json`) соблюдаются в реальном деплой-пайплайне (это уже вопрос DevOps-процесса, а не самих lock-файлов).

## 7. Нестабильные версии (`minimum-stability: dev`/`dev-master`)

- `garnet-framework/composer.json`: `"minimum-stability": "stable"` — явно задано, стабильные версии. ОК.
- `IRabi/composer.json`: `minimum-stability` не указан явно → Composer использует значение по умолчанию `"stable"`. ОК, никаких `dev-master`/`dev-*` зависимостей в требованиях не обнаружено ни в одном `require`.
- Единственная "нестандартная" версия во всём дереве — сам `phpcraftdream/garnet-framework` зафиксирован как `v0.1.0-alpha13` (alpha-релиз, но это тег стабильной ветки, не `dev-*` alias) — риск описан в разделе 2.2.
- В npm: `@typescript/native-preview: "latest"` (и в корневом `package.json` IRabi, и в `FrontBuilder/package.json`) — использование тега `latest` вместо зафиксированного диапазона версий является анти-паттерном для воспроизводимости сборки (though lock-файл фиксирует фактическую резолвленную версию `7.0.0-dev.20260623.1` — важно: это **dev-preview** пакет TypeScript от Microsoft, предназначенный для экспериментального нативного тулчейна, используется только для `typecheck`/IDE, не участвует в рантайм-бандле). Рекомендация: заменить `"latest"` на явный диапазон в `package.json`, чтобы избежать непредсказуемых будущих `npm install` без `package-lock.json`.

## 8. Рекомендации (приоритизировано)

1. **Высокий приоритет — до поставки заказчику:**
   - Обновить `dompurify` во `FrontBuilder` с 3.3.3 до ≥3.4.12 (закрывает 12 XSS/bypass advisories, влияет на прод-бандл).
   - Обновить `lodash` во `FrontBuilder` с зафиксированной 4.17.23 до последней 4.18.x (закрывает Code Injection + Prototype Pollution, прямая прод-зависимость).
   - Провести юридическую оценку использования `zachweix/php-zmanim` (LGPL-2.1) — включить в NOTICE/лицензионную документацию поставки, согласовать с `01-legal-compliance.md`.
   - Обновить `postcss` до ≥8.5.10 в билд-пайплайне FrontBuilder.

2. **Средний приоритет:**
   - Обновить Composer CLI на build/CI-хостах до версии ≥2.4, чтобы иметь возможность регулярно гонять `composer audit` (сейчас недоступен из-за версии 2.3.7).
   - Устранить дублирование `mockery`/`mockista` в dev-зависимостях framework — оставить один mock-фреймворк.
   - Проверить фактическое использование пакета `lucide` (не `-react`) во FrontBuilder — удалить, если не используется напрямую.
   - Синхронизировать версии `guzzlehttp/psr7`, `twig/twig`, `symfony/*` между `garnet-framework/composer.lock` (собственный lock фреймворка) и `IRabi/composer.lock` (итоговый lock приложения) — расхождения затрудняют воспроизводимость сборки самого фреймворка в изоляции.
   - Санировать dev-кластер уязвимостей `@rspack/cli`/`webpack-dev-server` (`shell-quote`, `websocket-driver`, `node-forge`, `svgo` и др.) — не блокирует прод, но стоит закрыть перед передачей CI-конфигурации заказчику, чтобы не оставлять "видимые" critical/high находки в `npm audit`.

3. **Низкий приоритет / долгосрочно:**
   - Заменить `aura/cli` (не обновлялся с 2017) на поддерживаемую альтернативу (в дереве уже есть `symfony/console` как транзитивная зависимость — можно унифицировать CLI-слой).
   - Заложить в roadmap миграцию с Symfony 6.4 LTS на актуальный мажор после 2027 (LTS support horizon).
   - Заменить тег `"@typescript/native-preview": "latest"` на явный зафиксированный диапазон версий в обоих `package.json`.
   - Мониторить активность репозитория `zachweix/PhpZmanim` (единственный мейнтейнер) — рассмотреть vendor-fork на случай прекращения поддержки апстрима, учитывая, что это ядровая функциональность продукта.

## 9. Методологические примечания

- `composer audit` и `npm audit` запускались в режиме только чтения (без флагов `fix`), lock-файлы не изменялись.
- Версии для composer-пакетов сверялись по фактически зафиксированным `version`/`time` в `composer.lock` (не по диапазонам из `composer.json`).
- Для npm-пакетов использовались реальные находки `npm audit --json` (данные из npm Advisory Database) — это не оценочные, а зафиксированные CVE/GHSA записи на момент аудита.
- Часть системных дат в lock-файлах (`time`: например `2026-07-13`) указывает на дату, отличную от реальной календарной — интерпретировано как особенность тестового/сборочного окружения, не влияет на корректность анализа версий пакетов и их уязвимостей.
