# Префетч по намерению (P2 backlog) — контракт

## Главный вопрос: документ или JSON?

Ответ определяется тем, что уже реально происходит по клику — не заново
изобретаем, а смотрим на существующий механизм.

В приложении **все внутренние `<a href>`-переходы уже перехвачены**
(`HotClickInit.ts`, framework): клик по любой eligible-ссылке не делает
браузерную навигацию, а вызывает `goTo(href)` → `getHtml(href)` (обычный
`fetch` без кэша) → `PageLoader.swapBody()` подменяет `<body>` без перезагрузки.
`getHtml()` возвращает **весь HTML-документ**: острова гидратируются из
`data-props`, встроенных сервером в разметку (то же, что видно в
`admin-support-init`/`ticketsList` и т.п.) — отдельного JSON-запроса ПОСЛЕ
гидратации для начального состояния острова нет, всё уже в документе.

Значит для навигаций по ссылке вариант «префетчить JSON, который остров всё
равно запросит» — ложная дилемма: такого отдельного запроса не существует,
документ и есть единственный запрос. Префетч документа не тяжелее и не легче
альтернативы — он единственный вариант, который реально переиспользуется
кликом, потому что это буквально тот же вызов, который `goTo()` сделал бы сам.

Но не все ожидания сети — переходы по ссылке. Часть экрана меняет клиентское
состояние (открывает вкладку/модалку) и сама делает XHR за JSON — это не
проходит через `HotClickInit`, там `href` нет вообще. Для этого класса
единственный вариант — префетч JSON-эндпоинта, который вызовет тот же
обработчик клика.

**Решение: гибрид, но не «по типу ссылки», а по факту — навигация или
действие:**

| Класс | Что грузит клик сейчас | Что префетчим |
|---|---|---|
| Переход по `<a href>` (страница целиком) | `getHtml(href)` внутри `goTo()` | тот же `getHtml(href)`, через общий промис-кэш |
| Действие в уже загруженном острове (открыть вкладку/модалку) | свой `fetch(json-эндпоинт)` внутри `onClick` | тот же JSON-эндпоинт, через тот же промис-кэш |

Один и тот же кэш (#382) обслуживает оба случая — отличается только то, какой
URL в него кладут: `getHtml` в `GoTo.ts` и точечные `fetch()`-вызовы в
островах оборачиваются одной и той же функцией `prefetch(url)` /
`prefetchedFetch(url)`.

## Инвентаризация: что действительно ждёт сеть после клика

Смотрели на реальные переходы/действия, не на список экранов вообще.

### Класс А — переход по ссылке (документ целиком, готово к префетчу без правок вызывающего кода)

| Действие | Ссылка | Первый запрос сейчас |
|---|---|---|
| Каталог слотов → карточка эксперта | `<a href="/expert/id~{id}">` (EntityLinks) | `getHtml('/expert/id~{id}')` |
| Список диалогов → тред | `<a href="/system/im/?with={id}">` | `getHtml(...)` |
| Виджет поддержки → «Сообщения» | `.support-widget-im-link`, `hot-click` | `getHtml('/system/im/')` |
| Топ-меню: «Обзор слотов», «Брони», «Профиль», «Поддержка» | `TopMenu`/`SidebarMenu`, все ссылки через общий делегированный обработчик | `getHtml(href)` |
| Карточка тикета в клиентском `/support/` → сам тикет (не вкладка, отдельная страница у гостя) | зависит от реализации — если ссылка, то класс А | — |

Наведение/фокус на ЛЮБУЮ такую ссылку — безопасный кандидат на префетч без
изменения бизнес-логики: клик просто находит готовый промис вместо нового
`fetch`.

### Класс Б — действие внутри уже загруженного острова (JSON-эндпоинт, точечная правка на каждом месте внедрения)

| Действие | Компонент | Эндпоинт, который вызовет клик |
|---|---|---|
| Клик по строке тикета в админке | `AdminSupportIsland.openTicket` → `SupportTicketTab` | `~ticketDetail` |
| Клик по строке пользователя в админ-таблице | `UsersGrid`/`useUserTabs` → `UserDetailTab` | `~userDetail` |
| Смена недели в календаре слотов | `SlotsCalendarIsland` | эндпоинт недели (см. компонент) |
| Открытие модалки бронирования | `BookingForm` | данные слота, если довычисляются отдельным запросом |
| Открытие карточки клиента из тикета (D-209) | `TicketContext`/клиентский контекст | `~clientContext` |

Для класса Б наведение на СТРОКУ (не на ссылку) должно вызывать `prefetch(url)`
с теми же параметрами, что соберёт реальный `onClick` — придётся продублировать
сборку URL/параметров в двух местах (hover-обработчик и click-обработчик) или
вынести её в общую функцию, которую вызывают оба. Внедрение (#385) — по месту,
не одной правкой.

## Жёсткое правило безопасности

**По намерению префетчится только идемпотентный GET.** Гарантия — на уровне
самой функции `prefetch()`/`prefetchedFetch()` (#382), а не дисциплиной
вызывающего:

- `prefetch(url)` жёстко фиксирует `method: 'GET'` — сигнатура не принимает
  метод параметром вообще, только `url`. Вызвать с POST через этот путь
  невозможно синтаксически.
- `HotClickInit`/`GoTo.ts` и так работают только со ссылками (`<a href>`),
  которые по определению GET — мутирующие действия в этом приложении вызывают
  `sendPost`/`sendPostFormData` из другого модуля и никогда не оформлены как
  `<a href>` с `hot-click`.
- Для класса Б: наведение на кнопку-мутацию («Отменить бронь», «Удалить») НЕ
  должно триггерить `prefetch()` вообще — hover-обработчик вешается только на
  элементы, ведущие к экрану/детали (строка тикета, строка пользователя,
  ссылка), никогда на сами кнопки действия. Это проверяется тестом (#386):
  наведение и фокус на кнопку отмены не должно порождать сетевой запрос.

## Триггеры намерения (#383)

`mouseenter`/`focus` на элемент с debounce (не мгновенно — короткое наведение
проездом не должно тратить запрос) + `mousedown`/`touchstart` как более
надёжный «вот-вот кликнут» сигнал на мобильном, где `mouseenter` не работает.
Единая точка: делегированный обработчик на уровне `document`, аналогично
`generalLinkHandler` в `HotClickInit.ts`, а не отдельный слушатель на каждом
элементе.

## Публичный API (#384)

```ts
prefetch(url: string): void            // запускает GET, не ждёт результат, кладёт промис в кэш
prefetchedFetch(url: string): Promise<T>  // клик: отдаёт уже идущий/свежий промис, либо запускает новый (фолбэк)
```

`goTo()` в `GoTo.ts` меняет свой `getHtml(href)` на `prefetchedFetch(href)` —
единственная точка правки для ВСЕГО класса А сразу.
