## Резюме

Общий уровень зрелости обработки ошибок в проекте — **выше среднего для legacy/mid-size PHP-приложения**, но с несколькими конкретными пробелами, которые стоит закрыть перед финальной поставкой:

1. **Хорошая база**: production-вход (`run_web.php`) всегда регистрирует кастомный callback в `ErrorCatcher`, который в production-режиме (`isDev() === false`) отдаёт пользователю **только** generic-сообщение "Internal server error" — ни stack trace, ни пути к файлам, ни SQL наружу не утекают. И HTTP-ошибки, и фатальные PHP-ошибки логируются на диск.
2. **Главная находка (Medium-High)**: два вызова отправки письма в модуле авторизации (`sendCode`, `sendSuccessLogin` в `EmailAuthMiddleware.php`) выполняются синхронно в теле запроса и **не обёрнуты в try/catch** — сбой SMTP валит весь запрос авторизации/логина в 500, хотя во всех остальных 10+ сценариях (бронирование, IM, поддержка) команда уже правильно перевела уведомления на асинхronную очередь (`FwEmailQueueService`), что как раз является хорошим паттерном graceful degradation.
3. **Таймаут MySQL-соединения нигде не задан** (ни `MYSQLI_OPT_CONNECT_TIMEOUT`, ни что-либо эквивалентное) — при сетевых проблемах/перегрузке БД воркер PHP-FPM может зависнуть на системный TCP-таймаут вместо быстрого fail-fast. Аналогично не задан явный таймаут SMTP-сокета (используется `default_socket_timeout` из php.ini, обычно 60 c) — то есть при сбое внешнего SMTP-сервера запрос авторизации может провисеть до минуты, удерживая воркер.
4. **Health-check эндпоинт отсутствует полностью** — ни `/health`, ни `/status`, ни что-то подобное не реализовано ни в IRabi, ни во фреймворке (этот же пробел уже отмечался в `docs/handover-audit/12-production-readiness-devops.md`).
5. **Логи ошибок не содержат контекста запроса** (URL, account_id, IP) — только имя исключения/сообщение/файл/строка/stack. При расследовании инцидента невозможно сопоставить конкретную запись лога с конкретным пользователем/запросом без дополнительных костылей.
6. **Дедупликация логов по `md5(name+message)` с пропуском записи, если файл уже существует** — повторяющаяся ошибка логируется один раз за календарный день; при массовом сбое (например, реальном падении БД) в лог попадёт только первая запись, что затруднит понимание масштаба инцидента по времени.
7. **PHP 8.x deprecation-паттерны — не обнаружены.** Кодовая база чистая: нет `each()`, `create_function()`, `strftime()`, `utf8_encode/decode`, неявных nullable-параметров, недекларированных динамических свойств. Похоже, эта область уже была приведена в порядок в одном из предыдущих циклов аудита.
8. **Frontend-формы (бронирование, IM, поддержка) — обработка ошибок реализована корректно**: везде есть try/catch вокруг fetch-вызовов, пользователю показывается toast/alert с сообщением об ошибке, кнопки гарантированно разблокируются через `finally`/`withSending`. Зависших/немых UI не найдено.
9. **Изоляция модулей (circuit breaker) — в целом хорошая**: маршруты регистрируются лениво (`Router::add()` не инстанцирует контроллеры), поэтому рантайм-баг в одном контроллере не должен ронять несвязанные страницы. Единственный структурный риск — использование `ImController::URL` как константы класса при регистрации роута форсирует автозагрузку файла контроллера на КАЖДЫЙ запрос; синтаксическая/fatal-ошибка на уровне файла в любом из ~30 подключаемых таким образом контроллеров положит весь сайт целиком. Активного бага не найдено, но это архитектурная хрупкость.

### MEDIUM

**M1. Отправка email в flow логина/авторизации не защищена от сбоя SMTP и валит основной сценарий**
- Файл: `D:\dev\garnet\garnet-framework\Bundle\Modules\Auth\Middlewares\EmailAuthMiddleware.php`
- `sendCode()` (строка 610, вызывается из `processPhaseNullPost()` строка 367) и `sendSuccessLogin()` (строка 638, вызывается со строки 575) не обёрнуты ни в try/catch на месте вызова, ни внутри самих методов. Единственный try/catch в файле — строки 403/405, не относится к этим вызовам.
- Сценарий 1 (`sendCode`): пользователь запрашивает код авторизации по email → это **основная** операция эндпоинта, поэтому если SMTP недоступен/тормозит — весь POST `/auth` падает необработанным исключением → пользователь вообще не может начать логин. Это, строго говоря, ожидаемо (без письма код не доставить), но должно приводить к понятному ответу «попробуйте позже», а не к сырому 500.
- Сценарий 2 (`sendSuccessLogin`): на строке 575 к этому моменту аккаунт УЖЕ обновлён (`Account::touchAccount`, флаги согласия сохранены — по данным аудита) — то есть бизнес-результат (успешный логин) уже совершился в БД, но если после этого письмо-уведомление о новом входе не отправится (SMTP недоступен), пользователь получит 500 вместо успешного JSON-ответа, хотя логин фактически состоялся. Классический анти-паттерн «побочный эффект ломает уже совершённую основную операцию».
- Контраст: все связанные с бронированием/IM/поддержкой/подтверждением эксперта уведомления (`Common\Services\EmailNotifications.php`) корректно кладутся в очередь через `FwEmailQueueService::enqueue()` (`vendor\...\Bundle\Modules\Email\FwEmailQueueService.php:54-93`) и отправляются позже фоновым cron-процессом (`Common\Services\AppCronService.php:17-19`) с try/catch и retry на каждый элемент очереди (`FwEmailQueueService.php:126-154`). Только эти два места в auth-модуле остались синхронными и незащищёнными.
- Рекомендация (без внесения изменений в рамках этого аудита): обернуть оба вызова в try/catch с логированием, либо, что предпочтительнее и последовательнее с остальной кодовой базой, перевести их через `FwEmailQueueService` — для `sendCode` это потребует синхронной гарантии доставки в разумные сроки (либо short-timeout прямой отправки с fallback-сообщением «код отправляется, если не пришёл — попробуйте снова»).

**M2. Нет таймаута соединения с MySQL**
- Файл: `D:\dev\garnet\garnet-framework\Kernel\Db\Link\DbPool.php`, метод `newLink()`, строки 95-123.
- `mysqli_connect(hostname, username, password, database, port)` (строки 104-110) вызывается без `mysqli_options(MYSQLI_OPT_CONNECT_TIMEOUT, ...)` — во всём каталоге `Kernel\Db` нет ни одного упоминания `MYSQLI_OPT_CONNECT_TIMEOUT`/`ATTR_TIMEOUT`/`connect_timeout` (проверено grep'ом).
- `WorkDir\Config\db.ini` передаёт только `options[MYSQL_ATTR_INIT_COMMAND]`, который `DbPool::newLink()` дополнительно применяет через `real_query()` (строки 112-117) — остальные опции конфигурационно даже некуда положить.
- Сценарий: если сервер MySQL недоступен по сети (не отвечает RST/ICMP, а именно «висит», например, из-за firewall/перегрузки), `mysqli_connect()` будет ждать системный TCP connect timeout (десятки секунд, зависит от ОС), удерживая PHP-FPM воркер всё это время. При достаточном количестве одновременных запросов это может исчерпать пул воркеров быстрее, чем сработает любой health-check/алерт.

Проблема именно в фазе установления соединения, не в фазе выполнения запроса.

**M3. Нет явного таймаута SMTP-сокета**

**M4. Логи ошибок не содержат контекста запроса (URL, account_id, IP)**

**M5. Дедупликация `Logger::write()` может маскировать масштаб массового сбоя**
- `garnet-framework\Kernel\Io\Logs\Logger.php`, метод `write()`, строки 107-126: имя файла лога строится как `md5($name . $message)`, и если файл с таким именем уже существует за текущий день (строки 121-123), **новая запись не пишется вообще** (`return;` до `file_put_contents`).
- Сценарий: MySQL временно упал на 20 минут, за это время сотни запросов кидают идентичное (или почти идентичное — зависит от того, включает ли message динамические данные) исключение `DbException`. В лог попадёт только САМАЯ ПЕРВАЯ запись этого дня; время окончания/масштаб инцидента (сколько запросов пострадало, до какого времени) реконструировать по этому логу невозможно. Метод `append()` (строки 133-147) такого поведения не имеет (всегда дописывает), но для ошибок используется именно `write()`.

## Проверено — без находок

1. **Раскрытие stack trace/путей файловой системы конечному пользователю в production.** `ErrorCatcher::processError()` (`ErrorCatcher.php:26-43`) отдаёт "сырой" echo стека только если `$errorCallBack` не установлен — на HTTP-входе (`run_web.php:32-44`) callback установлен всегда. Внутри callback'а (`BaseController::internal_error_500`, `garnet-framework\Kernel\Io\Router\BaseController.php:35-45` → `ErrorTools::makeErrorPageHtml`/`makeErrorJsonArr`, `ErrorTools.php:13-26, 73-83`) детали показываются только если `$globals->isDev()` истинно. `isDev()` (`garnet-framework\Kernel\Core\GlobalReqParams\GlobalReqParams.php:152-163`) истинно только при явном `GARNET_DEV=1` либо одновременно localhost + встроенный PHP dev-сервер — на реальном проде всегда `false`. Проверено: в non-dev режиме HTML отдаёт только `"Internal server error."` (`ErrorTools.php:76`), JSON вообще не содержит ключ `details` (строки 16-23).
2. **Обработка сбоя подключения к БД на верхнем уровне.** Исключение при недоступной БД (`mysqli_connect` бросает `mysqli_sql_exception` при PHP 8.1+ дефолтном `mysqli_report`) не перехватывается локально, но перехватывается либо в `IoRunWeb::getResponse()`'s try/catch, либо (если возникло вне него) глобальным `set_exception_handler` из `ErrorCatcher.php:95-98`, который использует тот же production-callback — конечный пользователь в обоих случаях видит одну и ту же generic-страницу 500, не белый экран и не raw-трейс.
3. **Обработка сбоя отдельного SQL-запроса (не самого коннекта).** `DbMySQLiLink::query()` (`garnet-framework\Kernel\Db\Link\DbMySQLiLink.php:64-98`) ловит `Throwable` и перебрасывает как `DbException` с текстом запроса — попадает в тот же путь логирования+generic-500, что и выше. Все виды сбоя запроса (deadlock, too many connections, query timeout) обрабатываются одинаково корректно на уровне ответа пользователю.
4. **Уведомления о бронировании/сообщениях/тикетах поддержки/одобрении эксперта — НЕ ломают основной HTTP-запрос при сбое SMTP.** Все 10 сценариев в `Common\Services\EmailNotifications.php` идут через `FwEmailQueueService::enqueue()`/`enqueueToMany()` (только INSERT в таблицу очереди внутри того же запроса) — реальная отправка через SMTP происходит асинхронно из cron-задачи (`Common\Services\AppCronService.php:17-19`), с try/catch и retry на элемент очереди (`FwEmailQueueService.php:126-154`). Сбой SMTP в этом потоке никак не влияет на HTTP-ответ пользователю по основной операции.
5. **Внешние HTTP API вызовы.** Grep по `curl_init`, `GuzzleHttp`, `file_get_contents('http://...')`, Symfony HttpClient в `Common/`, `Foreground/`, `Dashboard/`, `garnet-framework` — ноль совпадений. У приложения нет исходящих REST/API интеграций, кроме SMTP; соответствующий раздел про "таймауты на исходящие HTTP-запросы" в этой части неприменим (риска нет за отсутствием самих вызовов).
6. **Uncaught-исключения и fatal errors реально пишутся в постоянный лог, а не теряются.** Подтверждено на двух независимых путях: `run_web.php:31-44` (callback внутри `ErrorCatcher::init`) и `IoRunWeb.php:114-123` (`logExceptionAndGet`, вызывается из `getResponse()` строка 151) — оба пишут в `Logger::ERROR_LOGGER` до формирования HTTP-ответа.
7. **Утечка паролей/токенов/номеров карт в логи при ошибках сериализации.** Проверены `Common/`, `Foreground/`, `Dashboard/` на предмет логирования `$_POST`/`$_REQUEST`/полных payload'ов или `json_encode`/`serialize`/`var_export`/`print_r` рядом с логированием — конкретных совпадений с полями пароль/токен/секрет/карта не найдено. Единственный сколь-нибудь релевантный код — `SysLogController` (см. LOW L2), но там нет активного пути передачи чувствительных полей на сегодняшний день.
8. **Frontend-формы бронирования, IM, поддержки — обработка ошибок присутствует и корректна.**
   - Бронирование: `Front\Islands\Bookings\BookingForm.tsx:52-67` — try/catch вокруг `sendPost`, состояние ошибки рендерится в `alert-danger` (строки 105-109), кнопка разблокируется через `withSending`/`finally`.
   - IM: `Front\Islands\Im\ImPageIsland.tsx:142-207` (`handleSendNew`, `handleReply`) — try/catch, toast об ошибке через `showToast(msg, 'danger')` (строки 171, 202), также трактует `{success:false}` как ошибку (строки 155-159, 192-195).
   - Поддержка: `Front\Islands\Support\SupportWidgetIsland.tsx:131-176` (`handleCreate`, `handleReply`) — try/catch, `showToast(err?.message || t.General_Error(), 'danger')` (строки 155, 173).
   - Ни в одном из трёх флоу не найдено зависшей кнопки/пустого alert/молчаливого игнорирования ошибки.
9. **PHP 8.x deprecation-паттерны, способные стать fatal в будущих версиях.** Проверено на `each()`, `create_function()`, `strftime()`, `utf8_encode`/`utf8_decode`, неявные nullable-параметры (`string $x = null` без `?`), недекларированные динамические свойства — по всем категориям 0 подтверждённых находок в `Common/`, `Foreground/`, `Dashboard/`, `garnet-framework/Bundle`, `garnet-framework/Kernel`. Кодовая база в этой части чистая, вероятно уже приводилась в порядок в рамках предыдущих циклов аудита.
10. **Изоляция модулей на уровне диспетчеризации маршрутов.** `Router::add()` (`garnet-framework\Kernel\Io\Router\Router.php:49-53`) только сохраняет class-string, не инстанцирует контроллер и не выполняет никакой код — реальный вызов метода происходит только для единственного совпавшего маршрута в `dispatch()`. Рантайм-ошибка в обработчике одного модуля (например, IM) не может повлиять на обработку несвязанного запроса (например, бронирования) на уровне логики выполнения (структурный риск на уровне автозагрузки файлов — см. LOW L4 — это отдельный, более узкий момент).
11. **Fallback-рендеринг 404/500-страниц при сбое самого Twig.** `BaseController::render404Fallback()` (`garnet-framework\Kernel\Io\Router\BaseController.php:86-101`) содержит хардкодный plain-HTML fallback на случай, если сам шаблонизатор не смог отрендерить страницу — то есть нет риска "ошибки при рендеринге страницы ошибки" оставить пользователя без ответа вовсе.
12. **Maintenance-режим при плановом деплое** — ранее уже проверялся (согласно вводным данным задания) и не является предметом повторной проверки в этом отчёте; отдельного эквивалентного механизма graceful degradation для runtime-сбоев (кроме поведения, описанного в п.1-3 выше) не требуется сверх уже подтверждённого generic-500 пути.
