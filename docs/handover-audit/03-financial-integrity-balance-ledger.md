## 1. Резюме

Архитектура денег: append-only журнал `balance_ledger` (источник истины) + денормализованный кэш
`account_balance.balance`, который пересобирается атомарным `INSERT … SELECT SUM(…) ON DUPLICATE KEY UPDATE`
(`FwAccountBalance::recalculate()`). Дебетовые операции защищены CAS-апдейтом
`UPDATE … SET balance = balance - ? WHERE … AND balance >= ?`. Идемпотентность booking-операций обеспечена
UNIQUE-индексами на леджере (`uq_ledger_ref` из M_0002 и дублирующий его `uq_idempotent` из M_0010).

База добротная: прямых read-modify-write по балансу в PHP нет, леджер в коде приложения иммутабелен,
округление возвратов не создаёт и не теряет копейки. Однако найдены реальные пути потери и «печати» денег:

- **4 находки High**: (H-1) окно гонки «CAS-списание ↔ recalculate», позволяющее увести баланс в минус;
  (H-2) неидемпотентная выдача возврата при отмене — деньги теряются безвозвратно при сбое между сменой
  статуса и записью refund; (H-3) возврат считается от **текущей** цены слота, которую эксперт может изменить
  после бронирования — создание/уничтожение денег и умышленный увод баланса эксперта в минус;
  (H-4) полное отсутствие механизма сверки — расхождения из H-1…H-3 в проде обнаружить нечем.
- **5 находок Medium**: дубли `top_up`/`manual` (NULL-ref не покрывается UNIQUE-индексом, фронт не шлёт
  `X-Idempotency-Key`); обход штрафа за отмену через гонку со статусом; отрицательные балансы экспертов
  «by design»; TOCTOU в удалении слота с потерей денег пользователя; «бесплатное бронирование» при сбое
  между списанием и записью invoice.
- Ряд Low-находок (переполнение INT, FLOAT в демо-таблице `payments`, искажённая отчётность, документация,
  расходящаяся с кодом).

Отдельно (контекст, не дефект): `/balance/~topup` — любой аутентифицированный пользователь **сам себе**
зачисляет до 1 000 000 за запрос без ограничения количества запросов и без платёжного шлюза
(`FwBalanceController::post__topup`, строки 120–163). Если при поставке «под ключ» предполагаются реальные
деньги — это главная дыра всей системы; если баланс декларируется как виртуальный — это должно быть
зафиксировано в договоре поставки.

## 2. Находки

### HIGH

#### H-1. Гонка «транзиентное CAS-списание ↔ recalculate()» — обход overdraft-guard, баланс уходит в минус

**Файлы:**
- `Foreground/Controllers/SlotsController.php:316-325` (CAS-списание totalCost), `:371-404` (вставка invoice/payment), `:428-442` (finally → recalculate)
- `Foreground/Controllers/BookingsController.php:369-424, 440-442`
- `Dashboard/Controllers/DashboardFinanceController.php:391-418`
- `vendor/phpcraftdream/garnet-framework/Bundle/Modules/Balance/Tables/FwAccountBalance.php:42-57` (recalculate), `FwBalanceLedger.php:58-88` (addEntry → recalculate)

**Суть.** Списание при бронировании — двухфазное: сначала CAS-апдейт кэша
(`balance = balance - X WHERE balance >= X`), затем вставка ledger-записи `booking_invoice`, затем
`recalculate()` пересобирает кэш из леджера. Сам код честно называет CAS-списание «transient adjustment»
(SlotsController:310-315). Проблема: **между CAS-списанием и вставкой invoice кэш и леджер расходятся**, и
любой конкурентный вызов `recalculate()` того же аккаунта (а его вызывает КАЖДЫЙ `addEntry()`: пополнение,
возврат, завершение другой отмены, а также finally-блок другого параллельного бронирования) пересоберёт
кэш из леджера, **в котором списания ещё нет**, — и «воскресит» уже списанные деньги в кэше.

**Сценарий (баланс 100, стоимость слотов по 100):**
1. Запрос A (`post__book`, слот 1): CAS-списание проходит, кэш 100 → 0. Invoice ещё не вставлен.
2. Параллельно тот же пользователь делает пополнение на 1: `addEntry(top_up)` → `recalculate()` →
   `SUM(ledger)=101` → кэш становится **101** (списание A стёрто).
3. Запрос B (`post__book`, слот 2): CAS-проверка `balance >= 100` проходит (кэш 101), списание проходит.
4. A и B вставляют свои invoice; финальный `recalculate()`: `SUM = 100 + 1 − 100 − 100 = −99`.
   Итог: у пользователя два бронирования при деньгах на одно, баланс −99.

Вместо пополнения шаг 2 может выполнить: возврат по другой отмене (`tryAddRefund` → `addEntry` →
`recalculate`), finally-блок параллельного мульти-бронирования (SlotsController:438-441), ручная
корректировка админа. Окно — от CAS-апдейта до вставки invoice: в `SlotsController::post__book` внутри окна
выполняются per-slot SELECT'ы, `reserveSeat`, INSERT booking — десятки миллисекунд на слот, при пакетном
бронировании окно пропорционально числу слотов. То же окно есть у дебетовой ручной корректировки
(DashboardFinanceController:391-417: CAS-списание → INSERT manual → recalculate).

**Последствие:** отрицательный баланс там, где бизнес-логика его не предусматривает; «двойная трата»
одного остатка. Эксплуатируется намеренно (скриптом: параллельные booking + topup/refund) или всплывает
само под нагрузкой.

**Рекомендация:** сделать вставку леджер-записи единственной фазой изменения денег и проверять остаток
атомарно относительно леджера, например: `INSERT INTO balance_ledger (…) SELECT … WHERE (SELECT COALESCE(SUM(…))
FROM balance_ledger WHERE account_id=?) >= ?` (однооператорный guard), либо сериализовать операции одного
аккаунта (`GET_LOCK('bal_<id>')`, т.к. транзакции в фреймворке сознательно не используются), либо держать
overdraft-инвариант в кэше: убрать пересборку кэша из SUM в пользу инкрементальных CAS-дельт + периодическая
сверка (см. H-4).

#### H-2. Отмена бронирования неидемпотентна по деньгам: сбой между сменой статуса и refund = безвозвратная потеря денег пользователя

**Файлы:**
- `Foreground/Controllers/BookingsController.php:511-557` — CAS `status='cancelled'` (513-516), ранний выход
  «уже отменено — success» (518-521), и только ПОСЛЕ этого вставка refund-записей (549-556).
- `Foreground/Controllers/ExpertPanel/ExpertBookingsService.php:167-187` (`cancelBooking`), `:269-300`
  (`cancelBookedSlot`), `:340-355` (`cancelSlot`) — та же схема: refund только в ветке `affected === 1`.

**Суть.** Переход `pending/confirmed → cancelled` и запись возврата в леджер — две независимые операции без
транзакции. Если процесс упал (fatal, потеря соединения с БД, kill воркера, деплой) после CAS-апдейта
статуса, но до `tryAddRefund()`:
1. Бронирование уже `cancelled`, место освобождено.
2. Refund-записей в леджере нет: пользователь заплатил, эксперт оставил себе оплату.
3. **Повторная попытка ничего не чинит**: повторный `post__cancel` попадает в ветку `affected === 0` и
   возвращает `success` (BookingsController:518-521), НЕ пытаясь довставить refund; экспертные отмены —
   аналогично (молчаливый `success` при `affected !== 1`).

Идемпотентный `addEntry(booking_refund, booking, id)` защищает от **двойного** возврата, но система нигде
не делает retry для **недовыполненного** возврата. В сочетании с H-4 (нет сверки) потеря необнаружима.

Зеркальная полу-проблема: в паре refund-записей сначала кредитуется пользователь, потом дебетуется эксперт
(BookingsController:552-555; ExpertBookingsService:183-186). Сбой между ними = в системе создано `cost`
денег из воздуха (пользователю вернули, с эксперта не сняли).

**Рекомендация:** в ветке «уже cancelled» не возвращать success сразу, а проверять наличие refund-записей в
леджере и довставлять недостающие (идемпотентность это позволяет — UNIQUE-индекс сам отбросит дубль);
компенсационный cron «cancelled-бронирования платных слотов без booking_refund в леджере».

#### H-3. Возврат считается от текущей цены слота, а не от суммы invoice; цена редактируема при активных бронированиях → создание/уничтожение денег

**Файлы:**
- `Foreground/Controllers/BookingsController.php:532-556` — `$cost = (int)($slot2['cost'] ?? 0)` читается
  из слота В МОМЕНТ ОТМЕНЫ и передаётся в `computeRefundAmounts()`.
- `Foreground/Controllers/ExpertPanel/ExpertBookingsService.php:178, 265, 335` — то же (`$slotCost = (int)$slot['cost']`).
- `Foreground/Controllers/ExpertPanel/ExpertSlotsService.php:469-571` (`editSlot`) — редактирование
  разрешено при `status === 'free'` (477-479, CAS на 562), при этом **групповой слот с активными
  бронированиями остаётся `free`, пока не заполнен** (`booked_count < max_users` — статус `booked`
  выставляется только при заполнении, см. SlotsController:409-412). Смена `cost` не ротирует `uid`
  (ротация только при смене времени, 516-517) и никак не проверяет наличие активных бронирований.

**Сценарий A (пользователь теряет деньги):**
1. Эксперт создаёт слот: cost 1000, max_users 3.
2. Пользователь бронирует: invoice −1000, эксперту payment +1000. Слот заполнен на 1/3 → статус `free`.
3. Эксперт редактирует слот: cost → 100 (разрешено — слот `free`).
4. Эксперт отменяет бронирование (`cancelBooking`): refund пользователю **+100**, эксперту −100.
   Итог: пользователь потерял 900, эксперт оставил себе 900 за неоказанную услугу.

**Сценарий B (печать денег через сговор / два аккаунта):**
1. Слот cost 100, max_users 2. Аккаунт-«пользователь» бронирует: −100 / эксперту +100.
2. Эксперт поднимает cost до 1 000 000 (слот всё ещё `free`).
3. «Пользователь» отменяет pending-бронирование: refund **+1 000 000** ему, эксперту −1 000 000.
4. У «пользователя» +999 900 работоспособного баланса; эксперт в минусе на ~1 000 000 — минус ничем не
   ограничен (refund-дебет вставляется без overdraft-guard, см. M-3) и никогда не будет погашен.
   Система «напечатала» ~1 000 000 расходуемых денег.

**Рекомендация:** сумму возврата брать из леджера — из строки `booking_invoice` по `ref_id = booking_id`
(она иммутабельна и точна), а не из `slot.cost`; и/или запретить смену `cost` при существовании активных
бронирований (проверка + CAS-условие в UPDATE).

#### H-4. Нет ни одного механизма сверки: расхождения баланса, леджера и парности проводок невозможно обнаружить

**Факт:** во всём приложении (`Common/`, `Dashboard/`, `Foreground/`, `Common/Commands/`,
`AppCronService::registerTasks()` — задачи только `email-queue`, `complete-expired`,
`disable-stale-tokens`) **нет** ни cron-задачи, ни CLI-команды, ни админ-функции, ни теста уровня прода,
которые проверяли бы:
1. `account_balance.balance == SUM(ledger)` по каждому аккаунту (кэш vs журнал);
2. парность проводок: каждой `booking_invoice(user, X, ref)` соответствует `booking_payment(expert, X, ref)`,
   каждому refund-кредиту — refund-дебет той же суммы;
3. глобальный инвариант: `SUM(все is_credit=1) − SUM(все is_credit=0) == SUM(top_up) ± SUM(manual)`
   (booking-проводки в сумме дают ноль).

SQL вида `SUM(CASE WHEN is_credit=1 …)` встречается только в Playwright-тестах
(`Tests/cross-role/*.spec.ts`, `Tests/user/booking-time-guards.spec.ts`) — в проде недоступно.
Инцидент из H-1/H-2/H-3 (потерянный refund, распаренная проводка, минусовый баланс) не будет замечен
никем и никогда, пока пользователь сам не пожалуется. Для финансовой системы отсутствие сверки — само по
себе дефект поставки. Детальная рекомендация — в разделе 4.

### MEDIUM

#### M-1. `top_up` и `manual` пишутся в леджер без ref → UNIQUE-индекс их не дедуплицирует; фронт не использует Idempotency-Key → дубли при повторной отправке

**Файлы:**
- `FwBalanceLedger.php:73-74` — `'ref_type' => $refType ?: null, 'ref_id' => $refId ?: null`; комментарий
  (54-56) прямо признаёт: «Entries without a ref are never deduplicated» (MySQL считает каждый NULL
  уникальным в UNIQUE-индексе).
- `FwBalanceController.php:140-148` — `post__topup` → `addEntry(…, 'top_up', '', 0, …)` — без ref.
- `DashboardFinanceController.php:407-417` — `manual` с `ref_type/ref_id = null`.
- `IRabi.php:179-209` — `IdempotencyMiddleware` подключён и ждёт заголовок `X-Idempotency-Key`, но
  **ни один** фронтовый вызов его не шлёт (grep по `Front/**` — ноль вхождений; `BalanceIsland.tsx:63`,
  `BalanceAdjustModal.tsx` шлют обычный `sendPost`).

**Сценарий:** админ жмёт «Пополнить +1000» в `BalanceAdjustModal`; ответ теряется (таймаут прокси),
UI/человек повторяет запрос → две записи `manual +1000`. Для дебета хуже: повторный manual-дебет проходит
второй CAS и списывает дважды. То же с `post__topup` (double-click защищён только disabled-кнопкой на
время запроса; retry на сетевом уровне не защищён ничем). Заявленный в M_0010 idempotency-guard для этих
двух типов операций **не работает by construction**.

**Рекомендация:** генерировать client-side operation-id и слать `X-Idempotency-Key` (мидлвар уже готов);
либо писать его в `ref_type='op', ref_id=<id>` — тогда сработает существующий UNIQUE.

#### M-2. Обход штрафа за отмену: `previousStatus` читается до CAS

**Файл:** `Foreground/Controllers/BookingsController.php:474-547`.
`$previousStatus` берётся из SELECT (488), а CAS-отмена (513) принимает оба статуса
(`IN ('pending','confirmed')`). Гонка: бронирование `pending`; пользователь запускает отмену; параллельно
эксперт подтверждает (`ExpertBookingsService::confirmBooking`, CAS pending→confirmed). CAS-отмена
срабатывает уже по `confirmed`, но `$previousStatus === 'pending'` → `computeRefundAmounts()` идёт по
ветке полного возврата (658-659) вместо штрафной. Пользователь получает 100% вместо `100−penalty%`;
эксперт теряет причитающийся штраф. Деньги в системе не создаются (симметричные проводки), но
перераспределяются вопреки бизнес-правилу, причём гонку можно вызывать намеренно (отменять в момент
ожидаемого подтверждения). Аналогично обходится и запрет «отмена confirmed после начала сессии» (497-502).
**Рекомендация:** два раздельных CAS-а (сначала `WHERE status='confirmed'`, при 0 — `WHERE status='pending'`)
и вычисление возврата от фактически сработавшего перехода.

#### M-3. Отрицательные балансы экспертов заложены в модель: кредит в момент бронирования + безусловный дебет при возврате

**Файлы:** SlotsController:387-404 / BookingsController:406-423 (эксперту `booking_payment` немедленно при
создании pending-бронирования); BookingsController:553-555, ExpertBookingsService:184-186, 281-283, 352-354
(refund-дебет эксперта через `addEntry` — **без** какого-либо `balance >= amount`).
Эксперт получает деньги до оказания и даже до подтверждения услуги, может немедленно их потратить
(бронируя чужие слоты), после чего любая отмена (в т.ч. пользователем его pending-брони) уводит его в
устойчивый минус. Это делает overdraft-guard системно неполным: сумма отрицательных балансов экспертов —
прямой невозвратный убыток платформы; в связке с H-3 минус масштабируется произвольно.
**Рекомендация:** удерживать оплату на «эскроу» (кредитовать эксперта при `completed`, а не при создании
брони) — тогда refund вообще не трогает эксперта; либо ограничить величину допустимого минуса и вынести
решение в бизнес-требования поставки.

#### M-4. TOCTOU в `deleteSlot`: удаление слота параллельно с бронированием → деньги пользователя пропадают без возврата

**Файл:** `Foreground/Controllers/ExpertPanel/ExpertSlotsService.php:576-608`.
Проверка «нет активных бронирований» (592-600) и `deleteById` (602) не атомарны. Параллельное
бронирование, прошедшее `reserveSeat` + INSERT + списание в этом окне, оставляет: слот удалён, бронирование
`pending` живо, invoice списан. Дальше `post__cancel` читает слот (`selectById` → null), `$cost = 0`
(BookingsController:532-534) → **refund не выдаётся никогда**; экспертные отмены требуют живой слот.
Деньги пользователя заморожены навсегда (обнаружить нечем — H-4).
**Рекомендация:** `DELETE … WHERE id=? AND booked_count=0 AND NOT EXISTS(активные брони)` одним оператором
(+ проверка affected), а в `post__cancel` при отсутствии слота брать сумму возврата из `booking_invoice`
в леджере (общая починка с H-3).

#### M-5. Окно сбоя «бронирование создано, деньги не списаны» (бесплатное бронирование)

**Файлы:** `BookingsController.php:351-404` (порядок: INSERT booking → CAS-списание → INSERT invoice);
`SlotsController.php:336-405` (то же в цикле).
Сбой процесса после CAS-списания, но до вставки `booking_invoice`: бронирование `pending` существует,
а списание живёт только в кэше — первый же `recalculate()` (следующая любая операция аккаунта) вернёт
деньги. Итог: активное бронирование, за которое никто не заплатил, эксперт не получил `booking_payment`.
Обратный вариант (invoice вставлен, payment эксперта — нет) даёт распаренную проводку: пользователь
заплатил, эксперт не получил (деньги уничтожены). Ни то, ни другое не детектится (H-4).
**Рекомендация:** компенсационная сверка «pending/confirmed-брони платных слотов без invoice в леджере»
и «invoice без парного payment» (см. раздел 4) + довставка недостающих записей (идемпотентность позволяет).

### LOW

#### L-1. M_0010 при наличии дублей молча пропускает создание индекса и помечается применённой
`Migrations/Items/M_0010.php:49-56` — при существующих дублях миграция логирует WARNING и завершается
успехом; повторного запуска пайплайн не требует. Фактический риск смягчён тем, что эквивалентный UNIQUE
`uq_ledger_ref (account_id, ref_type, ref_id, entry_type)` создаётся ещё в `M_0002.php:86` — т.е. на любой
живой базе constraint уже есть, а M_0010 создаёт **второй дублирующий индекс** тех же колонок в другом
порядке. Побочный риск: DBA, увидев «duplicate index», может удалить «лишний» — и если удалит оба/не тот,
вся идемпотентность booking-проводок исчезнет молча (все `catch isDuplicateKeyError` превратятся в мёртвый
код, а прямые `insert` в контроллерах начнут плодить дубли). Рекомендация: оставить ровно один индекс,
задокументировать его как финансовый инвариант, добавить в сверку (раздел 4) проверку его существования.

#### L-2. Cron без защиты от параллельного запуска
`AppCronService` (runAll/runTask) не ставит lock. Денежных операций в cron сейчас нет
(`CronCompletionService::completeExpired` — только статусы slots/bookings, идемпотентно; expert payout
отсутствует как класс — деньги эксперту зачисляются при бронировании). Параллельный запуск сегодня грозит
максимум двойной отправкой email (`FwEmailQueueService::processQueue` — зависит от реализации claim'а) и
двойными строками CronLog. Но любой будущий денежный cron унаследует отсутствие lock'а. Рекомендация:
`GET_LOCK('cron_<task>', 0)` вокруг задачи.

#### L-3. Переполнение INT(11) кэша баланса достижимо легальными операциями
`top_up` до 1 000 000 за запрос без лимита числа запросов (FwBalanceController:135) + `manual` до 1 000 000.
~2150 пополнений доводят `SUM(ledger)` до > 2^31−1; `recalculate()` упадёт с out-of-range (strict mode) —
баланс аккаунта перестанет обновляться (все addEntry-операции аккаунта начнут падать после вставки строки
леджера). PHP-переполнения нет (64-bit, `(int)` кастинг корректно отсекает нечисловые/дробные входы;
отрицательные и 0 отклоняются на 355, 135). Рекомендация: BIGINT для `balance`/`amount` или суммарный
лимит на аккаунт.

#### L-4. `payments`/`payments_log`: суммы во FLOAT
`Common/Tables/Payments.php:17-18` — `sum`/`commission` FLOAT. Таблицы используются только демо-сидером
(`DevSeedService:1247-1291`) и нигде в бизнес-логике, но передаются заказчику в схеме. FLOAT для денег —
классическая ошибка точности; при подключении реальных платежей станет активной. Рекомендация: DECIMAL/INT
(копейки) или исключить таблицы из поставки.

#### L-5. Финансовая отчётность искажена (не влияет на балансы)

#### L-6. `ClearUserService` (test-mode CLI) рвёт парность леджера

#### L-7. Документация обещает транзакционность, которой нет

## 3. Проверено — находок нет

- **Атомарность overdraft-guard как таковая**: все три дебетовых пути (BookingsController:372-374,
  SlotsController:318-321, DashboardFinanceController:393-395) проверяют `balance >= amount` в том же
  UPDATE, что и списывают — отдельного SELECT-перед-UPDATE нет. (Проблема H-1 — не в самом CAS, а в
  транзиентности его результата.)
- **`recalculate()`**: один оператор `INSERT … SELECT SUM … ON DUPLICATE KEY UPDATE` — классическая
  lost-update-гонка двух recalculate устранена (FwAccountBalance:27-57); UNIQUE(account_id) на
  `account_balance` есть.
- **Идемпотентность booking-проводок**: `booking_invoice`/`booking_payment`/`booking_refund` всегда с
  `ref_type='booking', ref_id=<bookingId>`; UNIQUE-индекс + перехват duplicate-key
  (`CasUpdate::isDuplicateKeyError`, код 1062) делают повтор безопасным. Повторная отмена не даёт второго
  refund; user-cancel и expert-cancel не могут выдать возврат оба (CAS по статусу брони — ровно один
  победитель).
- **Округление возвратов** (`computeRefundAmounts`, BookingsController:646-667): `penalty = intdiv(cost*pct,100)`,
  `refund = cost − penalty`, пользователю и эксперту — одна и та же величина `refund`; штраф остаётся у
  эксперта внутри исходного `booking_payment`. Деньги не создаются и не теряются при любых pct (clamp
  0..100); при 100% проводок нет вообще — корректно. Суммы целочисленные (INT), копеек нет.
- **Ledger append-only**: ни одного UPDATE/DELETE по `balance_ledger` в коде приложения (кроме test-mode
  ClearUserService — L-6).
- **Двойное бронирование**: виртуальная колонка `active_dup_key` + UNIQUE `uq_active_booking` (M_0002:76-85)
  закрывает дубль активной брони на уровне хранилища; компенсации при duplicate-key (refund + releaseSeat)
  на месте; дубликаты slot_id внутри одного пакетного запроса корректно компенсируются (`refundedTotal`).
- **Ёмкость слота**: `reserveSeat`/`releaseSeat` — атомарные CAS, `GREATEST(...,0)` защищает от ухода в минус.
- **Валидация manual adjustment**: `(int)`-каст (инъекция типов невозможна), `amount<=0` и `>1e6`
  отклоняются, `note` 3..500, доступ owner/admin-only, rank-guard `actorMayActOn` (self-adjust заблокирован),

- **CSRF** на всех денежных POST-эндпоинтах foreground (book/cancel/topup); admin-эндпоинты за
  auth+rank-мидлварами.
- **`cost < 0`** отклоняется при создании/редактировании слота — отрицательная цена как способ
  реверс-перевода невозможна.
- **`completeExpired`**: денежных операций нет; повторный/параллельный запуск идемпотентен по статусам.
- **Vendor-копия фреймворка** совпадает с исходником garnet-framework (без локальных патчей денежного кода).

## 4. Рекомендация по сверке баланса и леджера (закрывает H-4, детектирует H-1/H-2/H-3/M-4/M-5)

Минимальный набор — одна CLI-команда `php garnet finance:audit` + cron-задача (с `GET_LOCK`), выполняющая
четыре SQL-проверки и пишущая расхождения в отдельную таблицу/лог с алертом админу:

1. **Кэш vs леджер** (детект H-1 и залипших транзиентных списаний):
   ```sql
   SELECT b.account_id, b.balance,
          COALESCE(SUM(CASE WHEN l.is_credit=1 THEN l.amount ELSE -l.amount END),0) AS ledger_sum
   FROM ir_account_balance b
   LEFT JOIN ir_balance_ledger l ON l.account_id = b.account_id
   GROUP BY b.account_id, b.balance
   HAVING b.balance <> ledger_sum;
   ```
   (плюс зеркальная проверка аккаунтов, имеющих леджер, но не имеющих строки баланса).
2. **Парность booking-проводок** (детект H-2/H-3/M-5): для каждого `ref_id` сумма
   `booking_invoice(is_credit=0)` должна равняться сумме `booking_payment(is_credit=1)`; сумма refund-кредитов
   — сумме refund-дебетов; refund не должен превышать invoice. Одним GROUP BY по `ref_id` с HAVING.
3. **Осиротевшие деньги** (детект M-4/H-2): брони `cancelled` платных слотов без `booking_refund`;
   активные брони платных слотов без `booking_invoice`; invoice с `ref_id`, не существующим в `bookings`.
4. **Глобальный ноль и отрицательные балансы**: суммарный booking-оборот = 0; список аккаунтов с
   `balance < 0` (сегодня легален только как следствие M-3 — каждый случай должен объясняться refund'ом).

Дополнительно: проверка существования UNIQUE-индекса идемпотентности на `balance_ledger` (см. L-1) как
smoke-инвариант при старте команды. Все четыре запроса read-only, их можно безопасно гонять хоть каждые
5 минут; починка расхождений — отдельной командой с ручным подтверждением (довставка недостающих парных
проводок идемпотентна благодаря существующим UNIQUE-индексам).
