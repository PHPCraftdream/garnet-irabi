# Аудит feature completeness: Admin/Dashboard-функционал IRabi

Дата аудита: 2026-07-18
Область: `Dashboard/`, `Front/Islands/AdminPanel/`, docs (`roles.md`, `architecture.md`, `business-analysis.md`, `workflows.md`, `expert-api.md`)
Метод: построчное сопоставление заявленных в документации прав/функций с реальной реализацией в PHP-контроллерах и React-островах. Изменения в код не вносились.

---

## 1. Резюме

Приложение готовится к поставке "под ключ", но аудит выявил **системный разрыв между документацией и реализацией именно в финансовом блоке и в блоке операционного управления бронированиями/слотами**, а также **критичный тупик в самом ядре экспертского workflow** (эксперт физически не может задать ссылку/место консультации и не может заполнить описание своего профиля через UI).

Сильные стороны: управление пользователями, модерация экспертов, CMS публичных страниц, support-тикеты, логи, комментарии — реализованы полно, без заглушек и мёртвых кнопок, с аудит-логом и email-уведомлениями.

Слабые места сосредоточены в четырёх зонах:
1. **Финансовый блок Owner** — управление комиссиями и выплаты экспертам заявлены в документации, но отсутствуют как функции; "отчёты" по факту являются сырыми списками без агрегации и экспорта.
2. **Операционное управление бронированиями/слотами** — Dashboard даёт Owner'у только просмотр (read-only), без возможности отменить чужую бронь, сделать точечный refund или снять слот с публикации.
3. **Экспертский профиль и слоты** — нет UI для заполнения bio/специализации эксперта и нет UI для указания формата (онлайн/офлайн) и ссылки/адреса встречи при создании слота — это делает "проведение занятия" нерабочим end-to-end для UI-пути.
4. **Системные настройки Admin** — из заявленного (БД, email, CORS/CSP, платёжные системы, миграции) реально через UI сделана только настройка email; остальное либо отсутствует полностью (CORS/CSP, платёжные шлюзы — которых в проекте нет вообще), либо доступно только через CLI/.ini (миграции, БД).

Заказчику до подписания финальной поставки следует либо реализовать перечисленные пробелы, либо явно скорректировать `docs/roles.md`/`docs/workflows.md`, чтобы не создавать ложных ожиданий относительно возможностей платформы.

## 3. Критичные пробелы (сведено по приоритету)

### 3.1 Эксперт не может задать формат/место консультации при создании слота — КРИТИЧНО
`Front/Islands/ExpertSlots/components/CreateSlotForm.tsx`, `BatchSlotWizard.tsx`, `ExpertSlotsIsland.tsx` (EditSlotModal) не содержат полей `is_online`/`location`, хотя backend (`Foreground/Controllers/ExpertPanel/ExpertSlotsService.php`, ок. строк 210-211, 264-265) их принимает и использует со значениями по умолчанию. Итог: все слоты создаются как "онлайн" с пустой ссылкой, и эксперт не имеет штатного способа когда-либо сообщить студенту, как подключиться. Это напрямую противоречит `docs/workflows.md:17` ("Определить формат (онлайн/офлайн)") и `docs/expert-api.md` (параметры `is_online`, `location` в POST `/expert/~slots`).

### 3.2 Профиль эксперта (bio/специализация/имя) нельзя отредактировать через UI — КРИТИЧНО
Таблица `ir_expert_profiles` заполняется только dev-сидами или ленивой пустой вставкой при первом слоте. Ни `/~profile_edit` (Foreground, общая форма профиля — работает только с `db_accounts_data`), ни `UserDetailPanel.tsx` (Dashboard — только просмотр `bio`/`specialization`, без `<input>`/`<textarea>`) не дают возможности заполнить эти поля. Публичная страница эксперта их отображает — то есть в проде эксперт навсегда останется с пустым описанием. Прямое нарушение `docs/roles.md:71-73` ("Управление профилем эксперта — фото, описание, специализация") и `docs/workflows.md:40-44`.

### 3.3 Owner не может управлять бронированиями/слотами/отменами из Dashboard — КРИТИЧНО
`DashboardBookingsController.php` (вкладки slots/bookings/expertCancellations/userCancellations) реализует исключительно построение read-only списков с фильтрацией; ни одного мутирующего эндпоинта (cancel/refund/block) не найдено. `AdminBookingsIsland.tsx`/`AdminCancellationsTab.tsx` — таблицы без колонки действий. Это противоречит тексту `docs/roles.md:51-52` ("Модерация контента → Управление доступностью слотов") — при этом стоит отметить, что таблица прав в §3 того же документа (`Слоты времени → Управление своими`) для Владельца уже стоит ❌, то есть документ сам с собой не согласован. Рекомендуется либо реализовать операционные действия, либо унифицировать формулировки в документе в пользу read-only-модели.

### 3.4 "Управление комиссиями" и "Выплаты экспертам" отсутствуют как функции — КРИТИЧНО
`docs/roles.md:55-56` прямо заявляет оба права Владельцу. В коде: комиссия платформы как концепция отсутствует полностью (расчёт, хранение, настройка — нигде, кроме мёртвой legacy-колонки `payments.commission` и хардкода 5% в dev-сидере). "Выплаты" сведены к ручной ad-hoc корректировке баланса (`DashboardFinanceController::post__adjustBalance`) без статусной модели и без интеграции с реальным переводом денег. Учитывая, что в проекте вообще нет платёжного эквайринга (баланс пополняется вручную), это может быть осознанным решением для текущего этапа — необходимо уточнение бизнес-контекста у заказчика.

### 3.5 Настройка платёжных систем и CORS/CSP заявлены для Admin, но не существуют — СРЕДНЕ/КРИТИЧНО в зависимости от бизнес-плана
`docs/roles.md:26,121` заявляет Admin ✅ / Owner 👁️ для "Платёжные шлюзы" и Admin ✅ для CORS/CSP. Ни того, ни другого нет ни в UI, ни в конфигурации (`WorkDir/ConfigExample/app.ini` не содержит соответствующих полей). Если по бизнес-плану платформа должна принимать реальные платежи через внешний эквайринг — это критичный пробел для запуска в продакшен.

### 3.6 Модерация эксперта: нет явного статуса "отклонено" и причины отказа — СРЕДНЕ
`ExpertsSection.tsx` использует единственный бинарный переключатель `IS_APPROVED` (Approve/Revoke), без поля "причина отклонения". Баннер эксперту на дашборде ("на рассмотрении") не меняется после явного отказа — эксперт либо решит, что заявка всё ещё обрабатывается, либо получит email, сформулированный как "revoked/suspended" (что вводит в заблуждение кандидата, который никогда не был одобрен). Стоит доработать UX, добавив явный статус "отклонено" с причиной.

### 3.7 Нет публичной формы "стать экспертом" — СРЕДНЕ (возможно осознанное решение)
Тип аккаунта `expert` назначается только через invite-токен владельца/админа либо ручное промоутирование в Dashboard (`DashboardUsersController::post__setUserType`). На публичном сайте нет ни формы заявки, ни объяснения "как стать экспертом". Может быть намеренной моделью "закрытая платформа по приглашениям", но нигде явно не задокументирована и не объяснена пользователю на UI.

### 3.8 "Финансовые отчёты" и "отчёты по активности" — это сырые списки без агрегации/экспорта — СРЕДНЕ
`docs/roles.md:59-60`. `fetchLedger` (300 последних записей) и `fetchRecentActivity` (последние 10 записей `AdminActionLog`) не дают выбора периода, группировки, экспорта в CSV/PDF. Реальная агрегация есть только в виде 4 метрик на главном дашборде (`fetchPlatformStats`).

## 4. Проверено — без находок (сильные стороны)

- **CMS публичных страниц** (`DashboardStaticPagesController` / `AdminStaticPagesIsland.tsx`, framework `StaticPagesAdminIsland.tsx`): зрелая реализация — markdown-редактор с live-preview, блочная модель (heading/text/image/gallery) с контролем видимости по ролям, загрузка изображений, SEO-поля (title/meta description/OG image), публикация/черновик, конструктор header/footer сниппетов с меню и колонками, история изменений через `EntityHistoryButton`. Заявленная в задаче на аудит возможность "редактировать содержимое публичных страниц без разработчика" — подтверждена полностью.
- **Support-тикеты** (`DashboardSupportController` / `AdminSupportIsland.tsx`, `SupportTicketTab.tsx` и вложенные компоненты): полный цикл — просмотр деталей, ответ пользователю с реальной отправкой email, внутренние заметки, смена статуса, назначение ответственного с валидацией прав, вложения с access-check, лента истории/breadcrumb. Ни одной заглушки не найдено.
- **Модерация экспертов** (одобрение/отклонение): реальный backend с каскадным обновлением `ir_expert_profiles`, email-уведомлениями, аудит-логом. Кнопки в `ExpertsSection.tsx` не декоративные.
- **Модерация комментариев** (`DashboardCommentsController` / `AdminCommentsSection.tsx`): скрытие/показ комментариев реализовано и работает, с аудит-логом и confirm-модалкой.
- **Системные логи** (`DashboardLogsController` / `AdminLogsViewerIsland.tsx`): 6 вкладок (actions/mails/requests/errors/cron/js-errors), реальные данные, полезны для диагностики (включая текст ошибок SMTP в mail log — закрывает пункт "уведомления об ошибках email-рассылки" из задачи на аудит).
- **Виджеты "требует внимания" на дашборде админа** (`AdminApprovalsWidget.tsx`, `AdminSupportWidget.tsx`, `AdminRecentActivity.tsx`, `AdminPlatformStats.tsx`): все работают на реальных данных (`DashboardMainController::fetchPendingApprovals/fetchOpenTickets/fetchRecentActivity/fetchPlatformStats`), не моки.
- **Доступ expertOnly / mayMutate**: продуманная реализация — GET-страницы `/expert` доступны неодобренному эксперту (показывает баннер "на рассмотрении"), но все мутирующие POST-эндпоинты (создание слотов, подтверждение брони) требуют approval, возвращая явный 403. Подтверждено тестами `Tests/expert/unapproved-expert*.spec.ts`.
- **Email-уведомления по ключевым событиям** (бронирование, отмена, одобрение/отклонение эксперта): реально ставятся в очередь через `FwEmailQueueService::enqueue`, не заглушки.
- **Автозавершение слотов** (`CronCompletionService::completeExpired`): реально переводит `booked → completed` по истечении времени, работает вопреки формально устаревшей пометке "в будущем" в одном из документов состояний.
- **Мёртвые кнопки / TODO / заглушки в React-компонентах AdminPanel**: целенаправленный поиск (`TODO`, `FIXME`, `not implemented`, `console.log`, `alert(...)`, `заглушка`, `stub`) по всей директории `Front/Islands/AdminPanel` и по `Dashboard/Controllers` не дал релевантных совпадений. Все проверенные `onClick`/`onChange` обработчики ведут к реальным backend-вызовам.
