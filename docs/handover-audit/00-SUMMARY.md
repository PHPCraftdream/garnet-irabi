# Сводное резюме аудита IRabi (Slotbook) перед поставкой заказчику "под ключ"

**Дата составления:** 2026-07-18
**Источники:** 17 независимых аудиторских отчётов (security + 16 handover-тем)
**Цель:** решение о готовности продукта к финальной передаче заказчику

---

## ОБЩИЙ ВЕРДИКТ: НЕ ГОТОВ К ПОСТАВКЕ "ПОД КЛЮЧ" В ТЕКУЩЕМ ВИДЕ

Продукт имеет зрелую техническую базу (добротная финансовая архитектура, 864 e2e-теста, 14+ раундов security-ревью), но содержит **7 жёстких блокеров**, без закрытия которых передача невозможна. Ориентировочный объём работ по блокерам: 4.5-9.5 рабочих дней разработки + организационные действия заказчика (РКН, реквизиты, секреты).

## БЛОКЕРЫ ДЛЯ ПОСТАВКИ "ПОД КЛЮЧ"

Ниже -- пункты, которые **абсолютно необходимо** закрыть ДО передачи заказчику.

### Блок A: Безопасность и авторизация
1. **HTTP -> HTTPS редирект + HSTS** (`12` C-2). Настройка на уровне nginx/хостинга. Проверить флаг `Secure` на session-cookie.

> Пункт "сброс процессных кэшей Session/Account между запросами" (`04` C-1) снят из блокеров — переклассифицирован в LOW после проверки реальной инфраструктуры прода (php-cgi, не php-fpm, процесс на запрос). См. примечание в разделе находок выше и `04-concurrency-race-conditions.md`. Остаётся дешёвой рекомендованной превентивной правкой на будущее, не блокирует поставку.

### Блок B: Деньги и бронирования
2. **Каскадная отмена броней при блокировке/разжаловании эксперта** (`02` C-1). При `IS_APPROVED=0` / `IS_DISABLED=1` -- отменять будущие pending/confirmed брони с полным возвратом и email-уведомлением.
3. **Запрет editSlot() менять cost/penalty при booked_count > 0** (`02` C-2, `03` H-3). Либо сохранять снапшот цены в строке брони, либо блокировать редактирование финансовых полей при наличии активных бронирований.
4. **Автоотмена pending-броней на прошедших слотах** (`02` H-1). Расширить `CronCompletionService` -- pending-брони на прошедших слотах переводить в `cancelled` с полным возвратом.
5. **Идемпотентность отмены: довставка refund при повторном вызове** (`03` H-2). В ветке "уже cancelled" проверять наличие refund-записей и довставлять недостающие.

### Блок C: Юридический комплаенс (152-ФЗ)
6. **Заполнить реквизиты оператора ПДн и контакты поддержки** (`01` F-01, `15` B-3). Заполнить `support_contact_email/phone/telegram` в `app.ini`, опубликовать полноценную политику с реквизитами.
7. **Реализовать права субъекта ПДн (экспорт/удаление)** (`01` F-02). Минимум: снять test-mode-гейт с `ClearUserService`, добавить админ-кнопку. Желательно: пользовательская страница `/account/privacy`.
8. **Подать уведомление в РКН** (`01` F-03). Организационное действие заказчика. Зафиксировать в передаточных документах.

### Блок D: Эксплуатационная готовность
9. **Автоматический бэкап БД + off-site копия** (`12` C-1). Cron ежедневного `db:backup`, ротация (7 daily + 4 weekly), выгрузка за пределы сервера.
10. **Внешний uptime-мониторинг** (`12` C-3). UptimeRobot/аналог с алертом на email/Telegram.
11. **Передача секретов заказчику** (`12` H-2). Новый SSH-ключ, смена паролей БД/SMTP, отзыв старого ключа, удаление прод-дампов с дев-машины.
12. **Документирование cron-задач** (`12` H-4). Точные crontab-строки в runbook.
13. **Ротация логов** (`12` H-3). Cron-задача удаления старых файловых и табличных логов.

### Блок E: Функциональная полнота
14. **UI для редактирования профиля эксперта** (`16` 3.2). Форма для bio/specialization/display_name -- без неё профиль эксперта навсегда пуст.
15. **UI для формата/места слота** (`16` 3.1). Добавить поля `is_online`/`location` в CreateSlotForm/BatchSlotWizard/EditSlotModal.
16. **Починить ссылки на Privacy/Cookies** (`15` B-1, B-2). Заменить `(/cookies)` на `{link:cookies}` или `/page/view~cookies`.

### Блок F: Зависимости
17. **Обновить DOMPurify** (`13` 2.3). С 3.3.3 до >=3.4.12 (12 XSS-bypass advisories).

## ОЦЕНКА ЗРЕЛОСТИ ПО ОБЛАСТЯМ

### Сильные стороны (GO или близко к GO)

- **Безопасность (security-audit)** -- 14+ раундов review, основные уязвимости закрыты. Из 15-го раунда только 1 Medium (account enumeration) и 3 Low. CSRF, injection, path traversal, upload -- проверены и защищены. Это сильнейшая сторона проекта.
- **Логические ошибки / edge cases (05)** -- кодовая база аккуратна. Единственная Medium -- нерабочие кнопки статусов support-тикетов. Даты, null-handling, enum'ы -- корректны.
- **Тестовое покрытие по потокам (11)** -- 864 Playwright-теста, 75 спеков с SQL-ассертами, настоящие гонки через Promise.all. Покрытие потоков -- GO. Проблема инфраструктурная (не в CI).
- **Зависимости (13)** -- нет CVE в PHP-пакетах. Основной риск -- DOMPurify в npm (легко обновить) и лицензия LGPL php-zmanim.
- **CMS / статические страницы (16 частично)** -- зрелая markdown-система с live-preview, блоками, SEO, историей.
- **Error handling (10)** -- production-режим не утекает стек-трейсы, frontend-формы обрабатывают ошибки корректно.

### Средние (условный GO, требуют точечных доработок)

- **Бизнес-логика бронирования (02)** -- финансовое ядро (ledger/CAS/idempotency) надёжно. Но два Critical в каскадах и мульти-слотах.
- **Финансовая целостность (03)** -- архитектура добротная (append-only ledger, CAS), но окна гонок и отсутствие сверки создают реальные риски потери/печати денег.
- **i18n (08)** -- словарь 898/898 ключей RU/EN в полном паритете. Но EN недостижим (язык захардкожен), а API-ошибки на английском видны в русском UI.
- **Email (09)** -- очередь с retry, журнал, dev-защита от SMTP. Но cron без lock'а, retry-окно крошечное, dead-letter без UI.
- **Контент/SEO (15)** -- canonical, OG-теги, брендированная 404. Но битые ссылки и пустые контакты.
- **Performance (06)** -- корректно на малых объёмах. Три системных бомбы при росте (EAV full scan, N+1 unread, "все слоты ради id").

### Слабые стороны (NO-GO)

- **Юридический комплаенс (01)** -- техническая база согласий хорошая, но "последняя миля" не пройдена: нет реквизитов, нет прав субъекта, нет РКН, нет retention. 3 блокера + 3 High.
- **Production readiness / DevOps (12)** -- это главная зона риска. Нет бэкапов, нет мониторинга, нет ротации, нет runbook, bus factor=1, секреты не передаются. 3 Critical + 5 High.
- **Конкурентность (04)** -- Critical в кэшах сессии (межпользовательская утечка). Это системная уязвимость авторизации.
- **Feature completeness / Admin (16)** -- эксперт не может заполнить профиль и указать место встречи. Финансовый блок Owner -- декларация без функции. Документация расходится с реальностью.
- **Целостность данных / миграции (14)** -- нет FK, нет rollback, M_0001/M_0002 не идемпотентны, документация схемы устарела.
