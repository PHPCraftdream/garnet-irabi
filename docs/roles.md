# Роли и права доступа

> **Источник правды — код.** Лестница рангов и хелперы:
> `Foreground/Params/UserEntityConfig.php`. Сами гейты стоят в конкретных
> экшенах контроллеров (`if (!static::isModerator()) …`), общего middleware
> на весь дашборд нет. Этот документ описывает фактическое поведение,
> проверенное чтением кода; при расхождении верен код, а документ — баг.

## 1. Две независимые оси

| Ось | Где хранится | Значения |
|---|---|---|
| Бизнес-роль | `db_accounts.type` | `user`, `expert` |
| Штатный ранг | флаги в `db_account_data` | `IS_MODERATOR`, `IS_OWNER`, `IS_ADMIN` |

Оси **ортогональны**: сотрудник с бизнес-ролью `user` остаётся полноценным
пользователем — бронирует слоты, платит, комментирует. Штатные флаги гейтят
только служебный интерфейс и никогда не прячут бизнес-функциональность
(см. комментарий у `UserEntityConfig::isUser()`).

Отдельные флаги состояния: `IS_APPROVED` (эксперт одобрен и виден публично),
`IS_DISABLED` (аккаунт заблокирован).

## 2. Лестница штатных рангов

```
RANK_ADMIN (3)  ⊇  RANK_OWNER (2)  ⊇  RANK_MODERATOR (1)  ⊇  RANK_USER (0)
```

Каждый старший ранг проходит проверку младшего:

```php
UserEntityConfig::isModerator()  →  isAdmin() || isOwner() || isModerator()
UserEntityConfig::isOwner()      →  isAdmin() || isOwner()
UserEntityConfig::isAdmin()      →  isAdmin()
```

Практический вывод: **администратор проходит любой служебный гейт системы**,
владелец — любой, кроме админских.

### Кто на кого может действовать

`UserEntityConfig::actorMayActOn($targetId)` — правило для действий,
меняющих чужой аккаунт (флаги, тип, баланс):

- нельзя действовать на самого себя;
- нельзя действовать на того, чей ранг **выше** твоего;
- **равные ранги управляют друг другом** — модератор↔модератор,
  владелец↔владелец, админ↔админ. Это осознанная политика для небольшой
  доверенной команды, принятая по итогам аудита (H-2 / F-08-04), а не
  недосмотр.

Система намеренно **не арбитрирует конфликты равных по рангу** — она их
допускает. Разбор «кто что сделал» обеспечивается журналом действий
(Dashboard → Логи), а не запретами.

## 3. Роли

### 3.1 Администратор — `IS_ADMIN`

Технический владелец системы, максимальный ранг. Может всё, что может
владелец и модератор, плюс эксклюзивно:

- **очередь писем** `/admin/email-queue/` — просмотр и ручной повтор
  отправки (`DashboardEmailQueueController`, гейт `isAdmin()`; повтор
  переводит письмо обратно в отправку, поэтому скрыт от остальных);
- **назначение `IS_OWNER` и `IS_ADMIN`** (`DashboardUsersController::post__setUserFlag`);
- **поиск по телу письма и метаданным** в почтовом журнале
  (`DashboardLogsController::mailsGridConfig` — остальным доступен поиск
  только по адресату, теме, типу, статусу и тексту ошибки).

### 3.2 Владелец — `IS_OWNER`

Бизнес-управление платформой. Всё, что может модератор, плюс:

- **корректировка баланса** пользователя `/admin/finance/`
  (`canAdjust` / гейт `isOwner()`);
- **необратимая очистка персональных данных** аккаунта (`post__clearUser`);
- **статические страницы** `/admin/pages/`;
- **системные настройки** `/admin/system/`;
- **назначение модераторов** (`IS_MODERATOR`).

Не может: назначать владельцев и админов, работать с очередью писем.

### 3.3 Модератор — `IS_MODERATOR`

Ежедневная операционка:

- дашборд `/admin/dashboard/`;
- пользователи `/admin/` — список, карточка, флаги `IS_APPROVED` и
  `IS_DISABLED`, смена типа `user` ↔ `expert`, удаление фото;
- слоты и брони `/admin/bookings/`;
- комментарии `/admin/comments/`;
- финансы `/admin/finance/` — просмотр (без корректировки баланса);
- инвайт-токены `/admin/tokens/` — целиком;
- поддержка `/admin/support/`;
- логи `/admin/logs/` — просмотр;
- модерация личных сообщений (`ImController`).

### 3.4 Эксперт — `type = 'expert'`

- профиль: имя, фото, «о себе», часовой пояс (общая форма профиля,
  `UserEntityConfig::editFields()`);
- расписание: публикация слотов, стоимость, отмена;
- взаимодействие с записавшимися, комментарии;
- свои доходы и история выплат;
- панель `/expert/`.

Пока `IS_APPROVED = 0`, эксперт не появляется в публичном поиске, и его слот
нельзя забронировать даже по прямой ссылке — проверка дублируется в самой
транзакции бронирования (`UserEntityConfig::isApprovedActiveExpert()`).
Заблокированный (`IS_DISABLED = 1`) эксперт остаётся виден на публичной
странице в анонимизированном виде, без аватара, слотов и счётчиков.

> **Известный пробел.** Поля `bio` и `specialization` из таблицы
> `expert_profiles` показываются на публичной странице эксперта и в карточках,
> но заполнить их **негде**: строка создаётся лениво с пустыми значениями
> (`ExpertPanel/ExpertSlotsService.php`), формы редактирования нет ни в
> `/expert/`, ни в дашборде. Непустыми они бывают только у dev/test-сидов
> (`DevSeedService`, `TestScopeSeedService`). См. `docs/handover-audit/16-feature-completeness-admin.md`.

### 3.5 Пользователь — `type = 'user'`

- профиль, часовой пояс, уведомления;
- поиск экспертов и фильтры;
- бронирование и оплата;
- история консультаций `/bookings`;
- комментарии и рейтинг экспертов.

## 5. Смена ролей и флагов

| Действие | Кто может |
|---|---|
| `user` → `expert` и обратно | модератор+ |
| Одобрение эксперта (`IS_APPROVED`) | модератор+ |
| Блокировка аккаунта (`IS_DISABLED`) | модератор+ |
| Назначение модератора (`IS_MODERATOR`) | владелец+ |
| Назначение владельца (`IS_OWNER`) | только админ |
| Назначение админа (`IS_ADMIN`) | только админ |

Любое из этих действий дополнительно проходит `actorMayActOn()` — на себя и
на старших по рангу нельзя.

## 6. Хранение в системе

```
db_accounts.type              ENUM('user','expert')
db_account_data (param/value) IS_ADMIN, IS_OWNER, IS_MODERATOR,
                              IS_APPROVED, IS_DISABLED
```

Штатные флаги — **независимые биты, не перечисление**: один аккаунт может
нести любую их комбинацию (например `IS_ADMIN = 1` и `IS_OWNER = 1`
одновременно). Ранг вычисляется по старшему выставленному флагу —
`UserEntityConfig::rankLevel()`.

Точки входа для проверок:

```php
UserEntityConfig::isAdmin() / isOwner() / isModerator()  // гейты служебного UI
UserEntityConfig::isUser() / isExpert()                  // бизнес-роль, ортогонально
UserEntityConfig::actorRankLevel() / accountRankLevel()  // ранг
UserEntityConfig::actorMayActOn($targetId)               // правило действия
```
