# IRabi — операционный runbook (для администратора)

Этот документ — перечень действий «что делать, когда что-то сломалось».
Он написан для **администратора сайта, а не для разработчика**: здесь нет
описания архитектуры, только конкретные команды и страницы, которые нужно
открыть/выполнить в момент инцидента.

## Как пользоваться

1. Найдите свой сценарий по заголовку ниже.
2. Выполняйте команды по порядку, сверху вниз.
3. Если в сценарии сказано «смотрите логи» — откройте Dashboard (см.
   раздел [Где смотреть логи](#где-смотреть-логи)) или конкретный файл.
4. Команды консоли даны в блоках `вот таких` — копируйте целиком.

### Где выполнять команды

Большинство команд — это **консольные команды на сервере** (PHP CLI).
Попасть в консоль сервера можно через SSH-терминал в панели хостинга
или с вашего компьютера командой `ssh <пользователь>@<хост>`. Все команды
`php garnet …` и `php run_cmd.php …` нужно запускать **в папке
приложения** — той, где лежат файлы `garnet` и `run_cmd.php` (в
4-папочной раскладке это папка `garnet-app-irabi`; точный путь на вашем
хостинге — см. [`deploy.md`](deploy.md), раздел `deploy.ini`).

Команды с суффиксом `:remote` (`maintenance:remote`, `ssh`, `ssh:test`,
`snapshot:pull`) — запускаются **с вашего локального компьютера** и сами
подключаются к серверу по SSH (нужен настроенный
`WorkDir/Config/ssh.ini`). Если вы уже в SSH-сессии на сервере —
используйте обычную форму без `:remote`.

> **Важно:** все команды, меняющие состояние сайта (`maintenance`,
> `db:restore`, `deploy:diff --apply`, и т.п.), выполняйте только когда
> понимаете, что они сделают. Если сомневаетесь — сначала прочитайте
> указанный раздел [`deploy.md`](deploy.md).

## Где смотреть логи

**Веб-интерфейс (без SSH):**

- **Dashboard → Журналы:** `https://<домен>/admin/logs/` — 6 вкладок:
  - `actions` — действия администраторов (кто что поменял);
  - `mails` — журнал отправленных писем (успех/ошибка, тема, получатель);
  - `requests` — HTTP-запросы;
  - `errors` — серверные ошибки (PHP exceptions);
  - `cron` — история запусков cron-задач (статус, длительность, вывод);
  - `js-errors` — ошибки в браузере пользователей.
- **Dashboard → Очередь писем:** `https://<домен>/admin/email-queue/` —
  текущее состояние очереди исходящих писем, счётчик «dead-letter»
  (письма, которые навсегда не отправились) и кнопка «Повторить» для
  ручного перезапуска сбойного письма.

**Файловые логи (через SSH):**

```bash
# Ошибки за сегодня (файл называется текущей датой):
tail -50 WorkDir/LogJournal/Errors/$(date +%Y-%m-%d).log

# То же самое с локального компьютера, без полного SSH-входа:
php garnet ssh "tail -50 WorkDir/LogJournal/Errors/\$(date +%Y-%m-%d).log"
```

## Сценарий 1. Сайт лежит (белый экран / 500 / не открывается)

```bash
# 1. Сайт в maintenance? Если да — это не авария, см. сценарий 2.
php garnet maintenance status

# 2. Свежие ошибки за сегодня:
tail -80 WorkDir/LogJournal/Errors/$(date +%Y-%m-%d).log

# 3. Работает ли БД? (если строк нет/ошибка соединения — проблема в MySQL):
php garnet migrate:status

# 4. Жив ли cron? (нет строк за последние сутки = cron сломан):
php garnet ssh "tail -30 WorkDir/Logs/cron-*.log 2>/dev/null"
```

Дальше:

- Много ошибок в `WorkDir/LogJournal/Errors/` после недавнего деплоя →
  см. [Откат релиза](#откат-релиза).
- Ошибки вида `Connection refused` / `Access denied` для БД →
  проверьте, что MySQL-сервер хостинга запущен, и что
  `WorkDir/Config/db.ini` содержит верные `host`/`user`/`password`
  (см. [Где лежат секреты](#где-лежат-секреты)). Перезапуск БД — на
  стороне панели хостинга.
- Ошибки «disk full» → см. [Кончается место на диске](#сценарий-5-кончается-место-на-диске).

## Сценарий 2. Сайт в заглушке после деплоя (maintenance сам не снялся)

**Это защитное поведение, а не баг.** Команда `php garnet deploy`
выполняет шаги в порядке: maintenance ВКЛ → резервная копия БД →
миграции → очистка кэша → maintenance ВЫКЛ. Если любой шаг **до**
последнего упал — maintenance **остаётся включённым намеренно**, чтобы
наполовину мигрированный сайт никогда не ушёл в «живой» режим.
Подробности: [`deploy.md`](deploy.md), раздел «Recommended workflow».

```bash
# 1. Подтвердить, что maintenance включён, и с какого времени:
php garnet maintenance status

# 2. Найти, какой шаг деплоя упал — смотрите вывод того самого
#    запуска `php garnet deploy` (он напечатал причину). Также:
tail -100 WorkDir/LogJournal/Errors/$(date +%Y-%m-%d).log
```

Дальше — один из двух путей:

**Путь А: починить причину и дозавершить деплой.** Устранив проблему
(например, ошибка миграции из-за несовместимой схемы), повторно
запустите `php garnet deploy` — он доведёт оставшиеся шаги и сам снимет
maintenance.

**Путь Б: откатиться назад** (если чинить нельзя / долго). См.
[Откат релиза](#откат-релиза): восстановите БД из резервной копии,
сделанной **перед** этим деплоем (её путь `php garnet deploy` напечатал
в самом начале вывода), затем откатите код.

В любом случае, когда сайт снова корректен — снимите заглушку:

```bash
php garnet maintenance off
# или с локального компьютера:
php garnet maintenance:remote off
```

## Сценарий 3. Нужно восстановить вчерашние данные (restore из бэкапа)

Ежесуточно cron-задача `db-backup` создаёт снимок БД в
`WorkDir/Backups/*.sql.gz` (хранятся 7 дневных + 4 недельных копии;
дополнительно см. [Где лежат секреты](#где-лежат-секреты) про off-site
копию).

```bash
# 1. Посмотреть доступные резервные копии (свежие сверху):
php garnet db:backup --list

# 2. ВКЛЮЧИТЬ maintenance — чтобы никто не писал в БД во время restore:
php garnet maintenance on

# 3. Восстановить выбранный файл (подставьте точное имя из шага 1).
#    ВАЖНО: restore САМ делает контрольный снимок текущей БД перед
#    перезаписью — на случай, если вы восстановили не то.
php garnet db:restore WorkDir/Backups/backup_20260719-030000_cron.sql.gz

# 4. Проверить, что сайт работает (maintenance ещё включён — смотрите
#    как админ через allow-list IP), затем снять заглушку:
php garnet maintenance off
```

**Что нужно знать перед restore:**

- **Restore теряет все записи, сделанные после момента снимка**
  (брони, сообщения, проводки баланса и т.д.). Необратимо.
- **Restore НЕ откатывает код приложения** — только данные. Если релиз
  менял и код, и схему БД, нужно отдельно откатить код (см.
  [Откат релиза](#откат-релиза)).
- ⚠️ **Процедура restore на «чистую» БД пока НЕ отрепетирована вживую**
  (открытый организационный пункт, задача приёмки #83 в
  [`customer-handover.md`](customer-handover.md)). Команды и формат
  файлов задокументированы и используются ежедневным бэкапом, но первая
  реальная восстановка требует **повышенного внимания**: держите
  maintenance включённым, проверяйте результат постранично, и держите
  под рукой путь к контрольному снимку, который restore делает перед
  перезаписью.

## Сценарий 4. Не уходят письма (пользователи не получают email)

```bash
# 1. Состояние очереди и счётчик dead-letter — откройте в браузере:
#    https://<домен>/admin/email-queue/
#    Если есть строки со status=error и пустым next_attempt_at — это
#    dead-letter: cron их больше не тронет. Кнопка "Повторить" вернёт
#    письмо в очередь.

# 2. Жив ли cron email-queue? Откройте https://<домен>/admin/logs/?tab=cron
#    — должны быть строки task_name=email-queue. Нет строк за последний
#    час = cron не настроен или сломан (см. раздел Cron ниже).

# 3. Журнал отправок и ошибок SMTP: https://<домен>/admin/logs/?tab=mails
#    — колонка error_log подскажет причину (auth failed / timeout / …).

# 4. Принудительно прогнать очередь вручную:
php run_cmd.php cron email-queue

# 5. Проверить SMTP-настройки (НЕ публикуйте значения здесь — только путь):
#    WorkDir/Config/email.ini
```

Частые причины:

- **cron не настроен на сервере** — без crontab-строки для `email-queue`
  письма вообще не отправляются (см. раздел [Cron-задачи](#cron-задачи)
  и [`deploy.md` → Cron](deploy.md#cron)).
- **Неверные SMTP-учётные данные** в `WorkDir/Config/email.ini` →
  `mails` покажет `auth failed` / `535 Authentication failed`.
- **Письмо застряло в dead-letter** — откройте
  `/admin/email-queue/`, нажмите «Повторить». Если снова падает —
  смотрите `error_log` в журнале писем.

## Сценарий 5. Кончается место на диске

```bash
# 1. Сколько места свободно:
df -h

# 2. Куда чаще всего "утекает" место — две самые объёмные папки:
du -sh WorkDir/Backups WorkDir/LogJournal

# 3. Размеры по всем подпапкам WorkDir (найти неожиданно большую):
du -sh WorkDir/* | sort -h
```

Куда обычно уходит место и что с этим делать:

- **`WorkDir/Backups/`** — ежедневные снимки БД. Должны автоматически
  прореживаться до 7 дневных + 4 недельных копий (задача `db-backup`
  делает это каждый запуск). Если копий больше — значит cron-задача
  `db-backup` давно не запускалась; прогоните вручную:
  `php run_cmd.php cron db-backup` (она сразу почистит по правилу).
- **`WorkDir/LogJournal/`** — файловые журналы. Прореживаются до 365
  дней задачей `log-rotation` (каждую ночь). Если папка растёт —
  прогоните вручную: `php run_cmd.php cron log-rotation`.
- **Сессии** (таблицы `session`/`session_data` в БД) — прореживаются до
  365 дней задачей `session-retention` (каждую ночь): `php run_cmd.php
  cron session-retention`.

> Если регулярно приходится чистить вручную — **сломан cron**. Проверьте
> наличие crontab-строк (см. [Cron-задачи](#cron-задачи)) и историю их
> запуска в Dashboard → Журналы → вкладка `cron`. Эти три задачи
  (`db-backup`, `log-rotation`, `session-retention`) спроектированы
  работать автоматически; ручной прогон — только разовая мера.

## Сценарий 6. Истёк SSL-сертификат (браузеры пишут «незащищённое соединение»)

**Сначала проверьте, действительно ли сертификат истёк:**

```bash
# С любого компьютера — посмотреть дату истечения сертификата:
curl -vI https://<домен> 2>&1 | grep -i "expire date"
```

**Важно понимать разделение ответственности:**

- Сам **SSL-сертификат** (Let's Encrypt / коммерческий) — это
  **инфраструктура хостинга, а не код IRabi**. Его выпускает и
  продлевает хостинг-провайдер (через свою панель управления) или
  собственный certbot на сервере. Приложение IRabi **не управляет**
  жизненным циклом сертификата.
- В коде IRabi есть `Common/Services/HttpsRedirectService.php` — это
  только **дополнительный слой** (defense-in-depth): принудительный
  редирект HTTP→HTTPS и HSTS-заголовок поверх того, что уже делает
  хостинг. Он **не заменяет** валидный сертификат и не чинит истёкший.

**Что делать:**

1. Зайдите в панель управления хостингом → раздел SSL/TLS-сертификаты.
2. Если сертификат истёк — перевыпустите его (большинство хостингов с
   Let's Encrypt делают это в один клик, либо включите автопродление,
   если оно было выключено). Конкретные шаги зависят от вашей панели
   хостинга — сверьтесь с её документацией.
3. После перевыпуска проверьте: `curl -vI https://<домен> 2>&1 | grep -i
   "expire date"` — дата должна быть в будущем.
4. **Особенность HSTS:** IRabi отправляет заголовок
   `Strict-Transport-Security: max-age=31536000` (1 год). Браузеры,
   которые хоть раз заходили на сайт, **запомнили** требование HTTPS на
   этот срок. Даже после починки сертификата отдельные браузеры могут
   ещё некоторое время показывать ошибку — это кэш HSTS у клиента, он
   обновится сам.

## Откат релиза

В IRabi **нет единой команды «откатить релиз»**. Откат — это два
независимых действия: откат **кода** и/или откат **схемы БД**.

### Откат кода приложения

```bash
# Откатить код к более старой git-ревизии (dry-run сначала —.review):
php garnet deploy:diff --since=<старый-git-ref>
php garnet deploy:diff --since=<старый-git-ref> --apply
```

`<старый-git-ref>` — это commit/тег последнего **работавшего** релиза
(например `v1.2.0` или хэш коммита). `deploy:diff` покажет/передаст
только изменившиеся файлы. Подробности: [`deploy.md`](deploy.md),
раздел «Routine code-only deploys».

### Откат схемы БД — только через restore

**Миграции IRabi однонаправленные (forward-only):** интерфейс миграций
содержит только `update()`, никаких `down()`/`rollback()`/`--revert` ни
на одном уровне. См. [`deploy.md`](deploy.md), раздел «Migrations:
forward-only, no rollback». Единственный способ вернуть схему БД к
прежнему состоянию — **восстановить БД из резервной копии, сделанной
перед миграцией**:

```bash
php garnet maintenance on
php garnet db:backup --list          # найти снимок ПЕРЕД миграцией
php garnet db:restore WorkDir/Backups/<нужный-файл>.sql.gz
# затем откатить код (см. выше) и снять maintenance:
php garnet maintenance off
```

**Когда у вас есть снимок перед миграцией:**

- `php garnet deploy` делает его **автоматически** в начале работы.
- Прямой `php garnet migration` (или `php run_cmd.php cron db-backup`
  вручную) — **НЕ делает**. Перед таким запуском **обязательно** сами
  возьмите снимок:
  ```bash
  php run_cmd.php cron db-backup     # пишет в WorkDir/Backups/
  php garnet db:backup --list        # убедиться, что свежий файл есть
  # и только потом:
  php garnet migration
  ```

## Cron-задачи

IRabi использует **7 cron-задач**. Полные crontab-строки для установки
на сервер — в [`deploy.md` → Cron](deploy.md#cron). Здесь — только имена
и кратко что каждая делает (полезно держать под рукой в момент
инцидента):

| Задача | Что делает | Как часто |
|---|---|---|
| `email-queue` | Отправляет письма из очереди (порциями по 50). **Без неё письма не уходят.** | каждую минуту |
| `complete-expired` | Переводит истёкшие слоты/брони в `completed`, отменяет зависшие `pending`. | каждые 10 мин |
| `disable-stale-tokens` | Отключает истёкшие/исчерпанные invite-токены. | каждые 15 мин |
| `db-backup` | Ежедневный снимок БД + хранение (7 дневных + 4 недельных) + off-site копия. | раз в сутки ночью |
| `log-rotation` | Чистит файловые журналы и таблицы логов старше 365 дней. | раз в сутки ночью |
| `session-retention` | Чистит таблицы сессий неактивных старше 365 дней. | раз в сутки ночью |
| `finance-audit` | Read-only сверка `account_balance` vs `balance_ledger` (только детект, без авто-починки). | раз в сутки ночью |

Запуск одной задачи вручную (для диагностики):

```bash
php run_cmd.php cron <имя-задачи>     # например: cron email-queue
php run_cmd.php cron list             # список всех зарегистрированных имён
```

Результат каждого запуска пишется в таблицу `cron_log` — смотрите в
Dashboard → Журналы → вкладка `cron`. Отсутствие записей за последние
сутки = cron на сервере не настроен или сломан.

## Где лежат секреты

Секреты (пароли, токены, ключи) **физически лежат на сервере** в
конфигурационных файлах папки `WorkDir/Config/`. Они **не в git** —
оттуда их никто не выкачает. Конкретные значения **здесь не
публикуются** намеренно; ниже — только **где какой файл искать**:

| Файл | Что внутри |
|---|---|
| `WorkDir/Config/db.ini` | Доступ к базе MySQL: `host`, `user`, `password`, `dbname`, `prefix`. |
| `WorkDir/Config/app.ini` | Настройки приложения: `base_url`, `timezone`, `env`. |
| `WorkDir/Config/email.ini` | Учётные данные SMTP-сервера для отправки писем (`host`, `user`, `password`, …). |
| `WorkDir/Config/backup.ini` | Доступ к WebDAV-хранилищу для off-site копии бэкапов (`url`, `user`, `password`). Если `url` пуст — off-site отключен, бэкапы хранятся только локально. |
| `WorkDir/Config/ssh.ini` | SSH-ключ для деплоя (`identity_file` или `identity_key`). |
| `WorkDir/Config/deploy.ini` | Пути на сервере (не секреты, но рядом). |

Шаблоны без секретов (только структура ключей) лежат в
`WorkDir/ConfigExample/` — они в git и безопасны для просмотра.

## Эскалация инцидента

Контакт для эскалации инцидента (телефон/email разработчика, сроки
реакции SLA) — **организационный пункт**, который заполняется при
передаче системы заказчику и **в этом документе намеренно не
продублирован**, потому что реальный контакт должен согласовываться
индивидуально. См. [`customer-handover.md`](customer-handover.md),
раздел «Что ещё должно быть передано заказчику» — пункт «контакт для
incident escalation и сроки реакции». Если этот пункт там ещё не
заполнен — это первый пробел, который нужно закрыть при приёмке: до его
заполнения у администратора нет формального канала связи с
разработчиком при аварии.
